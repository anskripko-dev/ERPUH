# Архитектура решения

**Наименование:** Контроль проведения документов по согласованию в 1С:Документооборот  
**Расширение:** `нп_КонтрольПроведенияПоДО` (префикс `нп_`)  
**Платформа:** 1С:Предприятие 8.3 / ERP. Управление холдингом  
**Назначение расширения:** адаптация (Customization)

---

## 1. Назначение

Решение обеспечивает серверный контроль проведения документов ERP до получения состояния **«Согласован»** в 1С:Документооборот (ДО), а также защиту согласованного (или находящегося на согласовании) документа от проведения по «старому» согласованию после существенных изменений.

Пилотный тип документа: `Документ.ПеремещениеТоваров`. Подключение других типов выполняется настройками без изменения кода.

---

## 2. Границы решения

| Входит в решение | Не входит |
|---|---|
| Запрет проведения без состояния «Согласован» | Автопроведение после согласования |
| Настройки по типу документа и организации | Правка типовых модулей БИД в основной конфигурации |
| Отбор по реквизитам (СКД) и участникам (включая/исключая) | Согласование через подсистему УХ как основной контур |
| Пересогласование при существенных изменениях (ДО 3) | Заимствование документов в расширение |
| Отображение статуса согласования на форме | Отдельная роль обхода контроля |

---

## 3. Контекст и зависимости

Решение опирается на типовую библиотеку интеграции с Документооборотом (БИД):

- связь ERP ↔ ДО: `РегистрСведений.ОбъектыИнтегрированныеС1СДокументооборотом`;
- состояние согласования: `РегистрСведений.СостоянияСогласованияВДокументообороте`;
- API ДО 3: `ИнтеграцияС1СДокументооборот3` (`ПрерватьОбработку`, `НачатьОбработку`);
- точки UX типовых форм: `МодификацияКонфигурацииПереопределяемый`, `СобытияФормКлиент`.

Источник истины для контроля проведения — **регистр состояний ДО** (не обязательный веб-вызов на каждое проведение).

## 4. Состав объектов

| Объект метаданных | Роль |
|---|---|
| `РС.нп_НастройкиКонтроляПроведенияПоДО` | Условия контроля: тип, организация, дата начала, отбор СКД, участники |
| `РС.нп_РазрешенныеРеквизитыПриСогласованииДО` | Белый список реквизитов (изменения без пересогласования) |
| `РС.нп_ПризнакиПересогласованияДО` | Признак «требуется пересогласование» по документу |
| `Перечисление.нп_ВидыСтрокУчастниковКонтроля` | Виды строк участников: Включая / Исключая |
| `Подписка.нп_КонтрольПроведенияПоДОПередЗаписьюДокумента` | Серверная точка контроля при записи/проведении |
| `ОМ.нп_КонтрольПроведенияПоСогласованиюДО` | Основная логика и API |
| `ОМ.нп_КонтрольПроведенияПоСогласованиюДОКлиент` | Вопрос подтверждения на форме |
| `ОМ.нп_КонтрольПроведенияПоСогласованиюДОПовтИсп` | Кэш настроек и состава групп |
| `ОМ.СобытияФормКлиент` (`&После`) | Подключение клиентского вопроса |
| `ОМ.МодификацияКонфигурацииПереопределяемый` (`&После`) | Статус согласования на форме |
| `Отчет.нп_СогласованныеНеПроведенныеПеремещения` | Согласованные, но не проведённые перемещения |
| `Подсистема.нп_КонтрольПроведенияПоДО` | Объединение объектов в интерфейсе |

Заимствуются справочники для типов измерений: `Организации`, `Пользователи`, `ГруппыПользователей`.

## 5. Логическая схема

```
Форма документа ──▶ СобытияФормКлиент (вопрос при существенных изменениях)
        │
        │ запись объекта
        ▼
Подписка ПередЗаписью: нп_КонтрольПроведенияПоДОПередЗаписьюДокумента
        │
        ▼
ОМ нп_КонтрольПроведенияПоСогласованиюДО
   1) применимость настройки (тип, организация, дата, отборы)
   2) существенные изменения → Прервать / Начать обработку ДО 3
   3) при проведении → разрешить только состояние «Согласован»
        │
        ├── РС настроек контроля
        ├── РС признаков пересогласования
        ├── РС состояний ДО + связи объектов
        └── API ДО 3 (ПрерватьОбработку, НачатьОбработку)
```

## 6. Алгоритм контроля

### 6.1. Применимость настройки

Контроль применяется, если одновременно:

1. для пары **полное имя документа + организация** есть запись с `КонтролироватьПроведение = Да`;
2. дата документа ≥ `ДатаНачалаДействия` (если дата начала заполнена);
3. выполнен отбор по реквизитам (СКД; пустой отбор = все документы типа);
4. текущий пользователь проходит отбор участников (пусто = все; сначала «Включая», затем «Исключая»);
5. включены константы использования интеграции/согласования через ДО.

Полноправные пользователи **не** освобождаются от контроля автоматически.

### 6.2. Запрет проведения

При `РежимЗаписи = Проведение` проведение разрешено только при состоянии **«Согласован»** в регистре ДО.
Иначе — отказ с сообщением вида: «Проведение документа невозможно. Печатная форма "…" не согласована в системе Документооборот.» (наименование берётся из настройки `НаименованиеПечатнойФормы`, для перемещения по умолчанию — «Накладная на перемещение»).

Запись без проведения и отмена проведения контролем проведения не блокируются (кроме сценария пересогласования).

### 6.3. Существенные изменения и пересогласование

**Защищённое окно:** есть связь с ДО и состояние ≠ `НеСогласован` (включая пустое состояние, `НаСогласовании`, `Согласован`).

**Существенные отличия** — любые отличия объекта от данных в ИБ по реквизитам шапки, дате и табличным частям, **кроме** реквизитов из белого списка `нп_РазрешенныеРеквизитыПриСогласованииДО`.  
Пустой белый список означает, что любое отличие считается существенным.

При существенных изменениях:

1. на форме — вопрос подтверждения;
2. на сервере — установка признака, вызов ДО 3: `ПрерватьОбработку` → `НачатьОбработку`;
3. проведённый документ принудительно распроводится (либо проведение не выполняется);
4. провести снова можно только после нового состояния «Согласован».

Проведение **без изменения данных** не инициирует пересогласование. Устаревший признак при уже полученном «Согласован» сбрасывается.

## 7. Клиентский и серверный контуры

| Контур | Механизм | Задача |
|---|---|---|
| Клиент | `СобытияФормКлиент.ПередЗаписью` → клиентский ОМ | Подтверждение изменений в защищённом окне |
| Сервер | Подписка `ПередЗаписью` на все `DocumentObject` | Гарантированный контроль независимо от формы |
| UX | `МодификацияКонфигурацииПереопределяемый` | Вывод статуса согласования на форме |

Документы в расширение не заимствуются: контролируемые типы задаются только записями регистра настроек.

## 9. Риски и ограничения

1. Неполный белый список приводит к лишним пересогласованиям — список уточняется в эксплуатации.  
2. Дата документа раньше порога `ДатаНачалаДействия` выводит документ из-под контроля.  
3. Недоступность ДО 3 при перезапуске обработки блокирует сценарий пересогласования до восстановления связи.  
4. Рассинхрон обмена БИД влияет на актуальность статуса на форме; контроль проведения опирается на регистр состояний.
