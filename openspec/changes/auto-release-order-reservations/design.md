## Context

В контуре продаж ERP УХ (механизмы обеспечения близки к УТ 11.5) резерв по `ЗаказКлиента` удерживается действием обеспечения в строках (`Резервировать`, `Отгрузить` и др.). Типовой «таймер резерва» отсутствует: снятие — ручная смена действия на `Не обеспечивать` (или `К обеспечению`) и проведение.

Заказчик: срок от **даты заказа**, исключать **полностью оплаченные**, частичная оплата — снимать, обособление — не трогать в v1. Реализация — расширение **НП** (`нп_`), без снятия с поддержки.

Перед кодированием зафиксировать **сборку** конфигурации (УТ 11.5.x / ERP УХ 3.2.x) и точные имена API обеспечения — они отличаются между ветками 11.4 / 11.5 / ERP.

## Goals / Non-Goals

**Goals:**

- Регламентное снятие «жёсткого» резерва по правилу: `НачалоДня(ДатаЗаказа) + N дней < НачалоДня(ТекущаяДатаСеанса)`
- Не трогать полностью оплаченные заказы
- Снимать при частичной / нулевой оплате
- Менять обеспечение через типовые процедуры, затем проводить документ
- Dry-run без записи в заказы + журнал фактических/планируемых действий
- Настройка N дней без правки кода

**Non-Goals (v1):**

- Срок от желаемой даты отгрузки / даты установки резерва / предоплаты как отдельный критерий
- Снятие обособленного обеспечения и `КорректировкаНазначенияТоваров`
- Исключения по менеджерам, складам, видам номенклатуры (заложить точки расширения, не реализовывать)
- Автоперевод в `К обеспечению` вместо `Не обеспечивать`
- Готовое Marketplace-решение; правки основной конфигурации
- UI «продлить резерв» на форме заказа (можно позже)

## Decisions

### 1. Расширение НП, не основная конфигурация

**Решение:** объекты в `uhnp.НП` с префиксом `нп_`.

**Почему:** кастомизация холдинга; обновления типовой без конфликта по метаданным доработки.

**Альтернатива:** внешняя обработка + регламент — возможна, но хуже для констант/журнала/прав; отклонена для целевого контура НП.

### 2. Критерий просрочки — дата заказа + N

**Решение:** просрочка, если `НачалоДня(Заказ.Дата) + ДнейРезерва <= НачалоДня(ТекущаяДатаСеанса)` (или строго `<` — зафиксировать при приёмке; по умолчанию: резерв живёт N полных календарных дней, снятие начиная с дня N+1).

**Почему:** явно согласовано заказчиком для v1; не требует хранения даты установки резерва.

**Альтернатива:** желаемая дата отгрузки — отложена (open question / v2).

### 3. Хранение N — константа + опционально РС

**Решение v1:** константа `нп_СрокРезерваЗаказаКлиентаДней` (Число ≥ 0). При `0` — регламент не снимает (или трактовать как «выключено»). Флаг `нп_АвтоснятиеРезерваВключено`, `нп_АвтоснятиеРезерваТолькоПросмотр` (dry-run).

**Почему:** минимум метаданных; достаточно для одного срока на всю ИБ.

**Альтернатива:** РС по соглашению/организации — v2 при появлении разных политик.

### 4. Полная оплата — не снимать; частичная — снимать

**Решение:** заказ считается «полностью оплаченным», если сумма оплат/зачётов по заказу (типовой контур взаиморасчётов / остатки по расчётам с клиентами в разрезе заказа — уточнить API сборки) ≥ сумме документа с допуском округления. Иначе (0% или частично) — кандидат на снятие.

**Почему:** бизнес-правило v1; частичный платёж не защищает весь резерв.

**Риск:** авансы без привязки к заказу, бартер, корректировки долга — см. Risks; на этапе design-review сверить эталонный запрос оплаты с типовым отчётом «Состояние выполнения заказа» / оплатой заказа.

### 5. Отбор кандидатов

**Решение:** запрос отбирает проведённые, не закрытые/не отменённые заказы, у которых есть строки с действием обеспечения, удерживающим складской резерв (типично `Резервировать`, `Отгрузить`; **не** `НеОбеспечивать`, **не** мягкое `КОбеспечению` как цель снятия — оно уже не держит жёсткий резерв). Исключить строки с заполненным назначением (обособление). Статусы «не трогать» (например, `КОтгрузке` / в процессе отгрузки) — список константой/РС после фиксации сборки.

**Алгоритм регламента (псевдокод):**

1. Если автоснятие выключено → выход  
2. Отобрать кандидатов запросом (дата, статус, действия, без обособления)  
3. Для каждого заказа: если полностью оплачен → журнал «пропуск: оплачен» → next  
4. Сформировать список строк к смене действия → `НеОбеспечивать`  
5. Если dry-run → только журнал «было бы снято» → next  
6. Иначе: загрузить объект, вызвать типовое заполнение обеспечения для выбранных строк, записать и провести; ошибки — в журнал, заказ не ломать частично без транзакции документа  

Пакетность: порциями (например, 50 заказов за запуск) с параметром, чтобы не держать долгую блокировку.

### 6. Снятие только через типовое API обеспечения

**Решение:** не писать напрямую в `ТоварыКОтгрузке` / резервы. Использовать экспортные процедуры модуля обеспечения конфигурации (имена зависят от сборки; ориентир УТ 11.5 — заполнение вариантов обеспечения в заказе). После смены — штатное проведение `ЗаказКлиента`.

**Почему:** в 11.5 действия и движения отличаются от 11.4; «в лоб» по регистрам ломает остатки и обновления.

### 7. Журнал и dry-run

**Решение:** РС `нп_ЖурналАвтоснятияРезервовЗаказов`:

| Поле | Назначение |
|---|---|
| Период / ДатаВремя | момент операции |
| ЗаказКлиента | ссылка |
| Режим | Факт / Просмотр |
| Результат | Снято / ПропускОплата / ПропускОбособление / Ошибка / … |
| Комментарий | текст (срок, N, сумма оплаты и т.д.) |
| КоличествоСтрок | сколько строк затронуто |

Права: чтение журнала — менеджерам продаж; запись — только регламент (привилегированный режим в модуле задания при необходимости).

### 8. Расписание

**Решение:** регламентное задание `нп_АвтоснятиеРезервовЗаказовКлиентов`, по умолчанию раз в час или ночной слот; предопределённое расписание + возможность отключить.

## Risks / Trade-offs

- [Неверный критерий «полной оплаты»] → ложные снятия или вечный резерв → сверка с типовым отчётом оплаты заказа на копии ИБ; допуски округления
- [Статус «К отгрузке» / частично отгружен] → срыв отгрузки → open question: статусы-исключения до реализации
- [Обособление частично в заказе] → снимать только необособленные строки; не трогать строки с назначением
- [Блокировка документа пользователем] → ошибка в журнале, повтор на следующем запуске
- [Нагрузка на большую базу] → порционный отбор, индексы по дате/проведению через типовые условия запроса
- [Расхождение API 11.5 vs ERP УХ] → spike 0.5–1 чд на конкретной сборке до массовой реализации
- [Частичная оплата снимает весь резерв] → осознанное правило v1; v2 может снимать пропорционально / только неоплаченные строки

## Migration Plan

1. Опубликовать расширение НП с объектами и заданием (задание выключено)
2. Задать `ДнейРезерва`, включить dry-run, запустить вручную на копии
3. Сверить журнал с ожиданиями менеджеров
4. Выключить dry-run на копии → приёмка
5. На бою: сначала dry-run 1–2 суток, затем боевой режим
6. Откат: выключить константу/задание или снять расширение; уже снятые резервы автоматически не возвращаются

## Open Questions

1. Точная сборка: УТ 11.5.x или только ERP УХ 3.2.8.x (имена API обеспечения)?
2. Список статусов заказа «не трогать» (к отгрузке, закрыт, на согласовании и т.д.)?
3. Граница дня: снятие в день N+1 или по истечении N×24 часов от даты-времени заказа? (в design заложено календарные дни от `НачалоДня`)
4. Нужен ли комментарий в заказе / запись в историю объекта при автоснятии?
5. v2: разные N по соглашению/организации; защита частичной оплаты?
