## ADDED Requirements

### Requirement: Configurable reservation timeout from order date
Система SHALL предоставлять в расширении НП (`нп_`) настройку срока резерва в календарных днях (`ДнейРезерва`) и признак включения автоснятия. Срок просрочки MUST вычисляться от даты документа `ЗаказКлиента`: заказ просрочен, если с начала дня даты заказа прошло не меньше `ДнейРезерва` полных дней (снятие допускается начиная с календарного дня N+1 относительно даты заказа). При `ДнейРезерва = 0` или выключенном автоснятии система MUST NOT изменять обеспечение заказов.

#### Scenario: Order older than N days is eligible by date
- **WHEN** автоснятие включено, `ДнейРезерва = 3`, дата заказа — 1-е число, текущая дата сеанса — 5-е число того же месяца, и заказ не исключён другими правилами
- **THEN** заказ считается просроченным по сроку резерва и является кандидатом на снятие

#### Scenario: Order within N days is not eligible by date
- **WHEN** `ДнейРезерва = 3`, дата заказа — 1-е, текущая дата — 3-е того же месяца
- **THEN** заказ НЕ является кандидатом на снятие по сроку

#### Scenario: Zero days disables release
- **WHEN** `ДнейРезерва = 0` или автоснятие выключено
- **THEN** регламент НЕ меняет действия обеспечения в заказах

### Requirement: Skip fully paid orders; release on partial payment
Система MUST исключать из снятия резерва заказы, признанные **полностью оплаченными** по типовому контуру оплаты заказа клиента (с допуском округления). Заказы с нулевой или **частичной** оплатой MUST оставаться кандидатами на снятие при прочих выполненных условиях.

#### Scenario: Fully paid order is skipped
- **WHEN** просроченный заказ полностью оплачен
- **THEN** система НЕ меняет обеспечение и фиксирует в журнале пропуск по причине оплаты

#### Scenario: Partially paid order is released
- **WHEN** просроченный заказ оплачен частично и есть строки с жёстким резервом
- **THEN** система снимает резерв с этих строк по правилам снятия (если не dry-run и нет иных исключений)

#### Scenario: Unpaid order is released
- **WHEN** просроченный заказ не оплачен и есть строки с жёстким резервом
- **THEN** система снимает резерв с этих строк по правилам снятия (если не dry-run и нет иных исключений)

### Requirement: Release hard reservation via supply actions
Система SHALL снимать складской («жёсткий») резерв, меняя действие обеспечения строк заказа на `Не обеспечивать` через типовые механизмы заполнения обеспечения конфигурации, после чего MUST проводить документ `ЗаказКлиента`. Прямая запись движений резерва в регистры накопления MUST NOT использоваться как способ снятия.

#### Scenario: Reserved lines become not to supply
- **WHEN** кандидат обработан в боевом режиме и в заказе есть строки с действием, удерживающим жёсткий резерв (например, `Резервировать` / `Отгрузить`)
- **THEN** у этих строк действие становится `Не обеспечивать`, документ проводится, резерв по ним освобождается штатными движениями

#### Scenario: Soft supply action is not a release target
- **WHEN** в строке уже установлено действие без жёсткого резерва (например, `К обеспечению` или `Не обеспечивать`)
- **THEN** система НЕ считает такую строку целью снятия жёсткого резерва

### Requirement: Skip isolated supply
Система MUST NOT изменять обеспечение строк (и при необходимости целых заказов), связанных с обособленным обеспечением (заполненное назначение / обособление). Такие случаи MUST фиксироваться в журнале как пропуск по обособлению.

#### Scenario: Isolated line is skipped
- **WHEN** в просроченном заказе строка с жёстким резервом имеет назначение обособления
- **THEN** система НЕ меняет действие обеспечения этой строки и отражает пропуск в журнале

#### Scenario: Mixed order releases only non-isolated lines
- **WHEN** в одном заказе есть обособленные и необособленные строки с жёстким резервом
- **THEN** снимается резерв только с необособленных строк; обособленные не изменяются

### Requirement: Scheduled job processing
Система SHALL выполнять отбор и обработку кандидатов регламентным заданием расширения по расписанию (и допускать ручной запуск). Обработка MUST быть устойчива к ошибкам по отдельному заказу: сбой одного документа MUST NOT отменять обработку остальных в том же запуске; ошибка MUST попадать в журнал.

#### Scenario: Job processes multiple orders
- **WHEN** регламентное задание запускается и есть несколько подходящих заказов
- **THEN** система обрабатывает их по правилам (с учётом порционности) и пишет результат по каждому в журнал

#### Scenario: Error on one order continues others
- **WHEN** проведение одного заказа завершается ошибкой (блокировка, отказ проведения)
- **THEN** в журнале фиксируется ошибка по этому заказу, остальные кандидаты продолжают обрабатываться

### Requirement: Dry-run and audit journal
Система SHALL поддерживать режим просмотра (dry-run), в котором отбор и решения те же, но документы заказов MUST NOT записываться и проводиться. Система MUST вести журнал: заказ, режим (факт/просмотр), результат, причина, количество затронутых строк, момент операции — чтобы менеджеры видели, что снято или было бы снято и почему.

#### Scenario: Dry-run does not change orders
- **WHEN** включён режим просмотра и есть просроченный неоплаченный заказ с жёстким резервом
- **THEN** обеспечение заказа не меняется, в журнале есть запись о планируемом снятии

#### Scenario: Production run writes journal after release
- **WHEN** в боевом режиме резерв успешно снят
- **THEN** в журнале есть запись с результатом успешного снятия и ссылкой на заказ

#### Scenario: Skip reasons are visible
- **WHEN** заказ пропущен из-за полной оплаты или обособления
- **THEN** журнал содержит соответствующую причину пропуска
