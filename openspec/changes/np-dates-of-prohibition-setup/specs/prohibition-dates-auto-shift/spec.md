## ADDED Requirements

### Requirement: Settings register for automatic prohibition dates
Система SHALL хранить правила автоматической установки в независимом непериодическом регистре сведений `нп_НастройкиАвтоматическойУстановкиДатЗапрета`.

Измерения (порядок на формах и в метаданных: Пользователь, Объект, Раздел):

- `Пользователь` — тип измерения «Пользователь» типового РС (`ОпределяемыйТип.АдресатЗапретаИзменения`). Пустое значение в настройке означает «для всех пользователей».
- `ОбъектДатыЗапрета` — тип измерения «Объект» типового РС (организация, касса, склад, банковский счёт организации, сценарий бюджетирования, сценарий товарного планирования). Пустое значение означает общую дату по разделу.
- `РазделДатыЗапрета` — `ПланВидовХарактеристикСсылка.РазделыДатЗапретаИзменения`. Пустое значение означает все разделы, допустимые для типа указанного объекта.

Ресурсы:

- `ЧислоДней` (N) — целое неотрицательное, включая 0; верхняя граница не задаётся.
- `Включено` — признак применения настройки регламентным заданием.

Регистр ведёт пользователь с полными правами. Роль `нп_БазовыеПраваДатЗапрета` MUST NOT давать чтение или запись этого регистра. Отдельные роли для настроек не создаются.

Для одного объекта допускается несколько настроек с разным N (по пользователям/группам и при необходимости по разделам). Разворачивание настройки по элементам справочника (все кассы, склады, счета) MUST NOT выполняться.

#### Scenario: Settings available to full rights only
- **WHEN** пользователь с ролью `нп_БазовыеПраваДатЗапрета` (без полных прав) открывает регистр настроек
- **THEN** регистр недоступен полностью, включая просмотр

#### Scenario: Empty object and empty section is addressee general date
- **WHEN** пользователь записывает настройку с незаполненными объектом и разделом
- **THEN** запись сохраняется; задание пишет в типовой РС одну запись с пустым разделом и пустым объектом (общая дата адресата)

#### Scenario: Personal object setting does not disable other sections
- **WHEN** включены настройки: «для всех» пустая пара N=1; у пользователя Скрипко — конкретная касса, раздел «Касса», N больше; задания отработали
- **THEN** в типовом РС есть запись Скрипко по этой кассе и полный набор родителя («для всех»): пустые раздел и объект с датой N=1; продажа и прочие разделы для Скрипко запрещены как до личной записи, а не остаются без запрета

#### Scenario: Personal cash keeps winning group's warehouse
- **WHEN** выигрывающая группа пользователя — «Продажи» (склад N=5, своей общей даты нет), «для всех» пустая пара N=1, у пользователя личная касса
- **THEN** в типовом РС у пользователя есть касса, копия склада группы «Продажи» и пустая пара с датой «для всех»; запреты кроме кассы такие же, как до личной записи

#### Scenario: Accountant with personal cash exception keeps group general date
- **WHEN** пользователь входит в группу «Бухгалтеры» (пустая пара N=30) и в группу «Продажи» (склад) и имеет личную настройку по кассе
- **THEN** общая дата этого пользователя в типовом РС равна дате группы N=30, а не дате «для всех» N=1; склад группы «Продажи» не копируется — до личной кассы выигрывали бухгалтеры, склад «Продажи» не действовал

### Requirement: Closed section-to-object map
Доработка SHALL охватывать закрытый перечень разделов и типов объектов (заявка 2.1.2 плюс раздел УХ `УчетПоМСФО` — как «Продажи», тип объекта организация):

| Тип объекта | Разделы |
|---|---|
| Организации | Авансовые отчёты, Бухгалтерский учёт, Ввод остатков, Внеоборотные активы, Внутреннее товародвижение, Закупки, Международный учёт, Продажи, Продажи между организациями, Производство, Регламентные операции, Розничные продажи, Сверки и корректировки задолженности, Финансовый контур, Ретро-бонусы клиентов, Ретро-бонусы поставщиков, Управление ремонтами, **Учёт по МСФО** (18) |
| Кассы | Касса |
| Склады | Складские операции (на ордерных складах) |
| БанковскиеСчетаОрганизаций | Банк |
| Сценарии | Бюджетирование |
| СценарииТоварногоПланирования | Планирование |

Появление новых разделов при обновлении конфигурации требует актуализации перечня. Доработка MUST NOT включать/выключать функциональные опции дат запрета по разделам, объектам и пользователям.

Сочетания объект/раздел в настройке:

| Объект | Раздел | Применение |
|---|---|---|
| Заполнен | Заполнен | Одна запись типового РС по указанным объекту и разделу |
| Заполнен | Не заполнен | Разворачивание в отдельные записи по каждому разделу, допускающему тип объекта |
| Не заполнен | Заполнен | Одна запись «общая дата по разделу» (без конкретного элемента справочника) |
| Не заполнен | Не заполнен | Одна запись типового РС: пустой раздел и пустой объект (общая дата адресата) |

#### Scenario: Organization with empty section expands to all org sections
- **WHEN** включена настройка: объект — организация, пользователь и раздел не заданы, N=5; задание запускается 20.08.2026
- **THEN** в типовом регистре по всем разделам, допускающим объект «организация», включая `УчетПоМСФО`, записана дата 15.08.2026, пользователь — «для всех пользователей»

#### Scenario: Cash desk setting expands to cash sections
- **WHEN** включена настройка: объект — конкретная касса, раздел не задан, N=3
- **THEN** настройка развёрнута в записи по всем разделам, допускающим тип «касса»

#### Scenario: Section-level setting does not overwrite object-level
- **WHEN** есть настройка по конкретной кассе (N=3) и настройка «объект не задан, раздел Касса, N=10»
- **THEN** создана одна запись с незаполненным конкретным элементом справочника по разделу «Касса»; кассы с собственной настройкой сохраняют границу N=3

### Requirement: Sliding absolute date calculation
Регламентное задание SHALL записывать в типовой ресурс `ДатаЗапрета` абсолютную дату: конец дня даты «текущая дата сеанса минус N календарных дней». N — число последних календарных дней **включая текущий**, доступных для редактирования.

Нормативная таблица (при расхождении с другим текстом верна таблица):

| N | Дата запуска | Записывается | Доступно для редактирования |
|---|---|---|---|
| 0 | 20.08.2026 | 20.08.2026 | с 21.08.2026 |
| 1 | 20.08.2026 | 19.08.2026 | с 20.08.2026 |
| 5 | 20.08.2026 | 15.08.2026 | с 16.08.2026 |
| 5 | 01.09.2026 | 27.08.2026 | с 28.08.2026 |
| 30 | 01.09.2026 | 02.08.2026 | с 03.08.2026 |

Документ, датированный днём границы, редактировать нельзя (подтверждено на стенде 22.08.2026). Дата сеанса — серверная дата сеанса задания; пересчёт по часовым поясам организаций не выполняется. Относительное `ОписаниеДатыЗапрета` при записи автоматической установки MUST быть пустым.

#### Scenario: N=5 on 20.08.2026
- **WHEN** включена настройка с N=5 и задание выполняется 20.08.2026
- **THEN** в типовой регистр записана дата 15.08.2026; документы с датой 15.08.2026 не редактируются, с датой 16.08.2026 — редактируются

#### Scenario: Next day shifts by one
- **WHEN** то же задание выполняется на следующий день
- **THEN** дата в типовом регистре сдвинулась ровно на один день

#### Scenario: Repeat run same day is idempotent
- **WHEN** задание повторно запускается в те же сутки
- **THEN** результат не меняется, дублей записей нет

### Requirement: Automatic records stay in sync; manual records are untouched
Задание SHALL актуализировать только автоматические записи типового регистра (комментарий начинается с `нп_авто`). Ручные записи (иной комментарий, в том числе пустой у записи типовой формы) MUST NOT изменяться и MUST NOT удаляться.

Автозаписи SHALL соответствовать текущим включённым настройкам после разворачивания по разделам: дата пересчитывается, комбинации, которых больше нет во включённых настройках, удаляются. Пока по комбинации действует запись `нп_СостояниеОткрытыхПериодов`, автоматическая установка эту комбинацию MUST NOT перезаписывать.

Типовую форму дат запрета не используют для той же политики, что и регистр настроек: иначе ручная запись останется и по правилам БСП может перекрыть автоустановку. Исключения, которые нельзя выразить настройкой, допустимо завести вручную — задание их не тронет.

#### Scenario: Manual warehouse date is untouched
- **WHEN** в типовой форме вручную задана дата по складу, настройки по нему нет
- **THEN** ни один запуск задания эту дату не изменяет и не удаляет

#### Scenario: Disabled setting removes auto record
- **WHEN** у настройки снят признак «Включено»
- **THEN** при следующем успешном запуске автоматическая запись этой настройки удалена из типового регистра; ручные записи не изменены

#### Scenario: Deleted setting removes auto record
- **WHEN** запись настройки удалена
- **THEN** поведение как при отключении: автозапись удалена, ручные записи не изменены

#### Scenario: Setting expansion shrinks
- **WHEN** настройку по организации без раздела (разворот в записи по разделам) заменили настройкой с пустыми объектом и разделом
- **THEN** устаревшие автозаписи по разделам организации удалены; записана общая дата адресата

### Requirement: Nightly job behaviour
Регламентное задание `нп_СдвигДатЗапретаИзменения` SHALL:

- выполняться ежедневно в 23:00;
- работать в привилегированном режиме, независимо от интерактивных прав;
- отключать типовую проверку даты запрета на время своей записи (`ДатыЗапретаИзменения.ОтключитьПроверкуДатЗапрета`);
- после записи вызывать `ДатыЗапретаИзмененияСлужебный.ОбновитьВерсиюДатЗапретаИзменения`;
- сначала восстанавливать истёкшие открытые периоды, затем применять настройки;
- при ошибке по одной настройке продолжать остальные; каждую ошибку писать в журнал регистрации с объектом, разделом и пользователем;
- при наличии ошибок по итогам выполнения отправлять уведомление администраторам ИТ;
- при пропуске дней не выполнять догоняющие запуски — обычный расчёт от текущей даты.

#### Scenario: One setting fails, others succeed
- **WHEN** при обработке одной настройки возникает ошибка
- **THEN** остальные настройки обработаны, ошибка в журнале регистрации, администраторам ИТ отправлено уведомление

#### Scenario: Typical write-off check unchanged
- **WHEN** пользователь записывает документ с датой внутри закрытого периода
- **THEN** выдаётся типовое сообщение об ошибке даты запрета; текст и поведение не изменились
