## ADDED Requirements

### Requirement: Period opening request document
Система SHALL предоставлять документ `нп_ЗаявкаНаОткрытиеПериода` со следующими реквизитами:

- `Организация` — обязательный реквизит шапки (печать и согласование); без роли детализации и без строк таблицы после согласования пишется общая дата адресата (пустой раздел и пустой объект), не 18 организационных записей;
- табличная часть `Объекты` — видна только роли `нп_УказаниеРазделовИОбъектовЗаявки` (и полноправному): сначала раздел, затем объект только того вида, который относится к разделу, с заголовком этого вида; если у раздела нет уточнения (тип объекта — организация), ячейка объекта только просмотр, колонку MUST NOT скрывать (иначе при смешанных строках пропадёт объект соседних строк);
- шапка как у типовых документов: номер, дата, организация сверху; статус согласования ДО — надпись (`LabelField`), не поле ввода; цвет подсказок `web:DimGray`, как на форме настройки.
- `ПериодС` — дата, начиная с которой требуется открыть данные; единственный реквизит, определяющий отсечку; даты окончания периода в документе нет;
- `СрокДействия` (K) — срок действия открытого периода в днях;
- `Пользователь` — пользователь или группа пользователей; **обязателен**: заявка всегда открывает период для конкретного пользователя или группы, а не «для всех»;
- `ПричинаОткрытия` — обязательное текстовое обоснование;
- `Ответственный` — пользователь, создавший заявку; заполняется автоматически, изменению не подлежит.

Пояснение на форме MUST быть постоянно видимым и понятным пользователю: согласованная заявка разрешает менять документы с даты «Открыть период с» и более поздние; срок — указанное число дней; когда срок закончится, запрет вернётся сам. Время регламентного задания в пояснении не указывать.

Форма документа и форма списка MUST показывать **статус согласования ДО** из типовых регистров `ОбъектыИнтегрированныеС1СДокументооборотом` и `СостоянияСогласованияВДокументообороте`: `На согласовании`, `Согласован`, `Не согласован`, «Связан с ДО, состояние не задано» или «Нет связи с Документооборотом». Поле только для просмотра.

#### Scenario: Document form shows Document Management approval status
- **WHEN** пользователь открывает заявку, связанную с ДО, в состоянии `НаСогласовании`
- **THEN** на форме документа поле «Статус согласования ДО» показывает «На согласовании»

#### Scenario: List form shows Document Management approval status
- **WHEN** пользователь открывает список заявок
- **THEN** в колонке «Статус согласования ДО» у каждой строки виден текущий статус из типовых регистров ДО

#### Scenario: User is mandatory
- **WHEN** пользователь записывает заявку без указания пользователя/группы
- **THEN** запись отклоняется

#### Scenario: Request filled without full rights
- **WHEN** пользователь с ролью `нп_БазовыеПраваДатЗапрета` и без полных прав создаёт и заполняет заявку
- **THEN** документ записывается; регистр настроек автоустановки и форма константы уведомлений недоступны

#### Scenario: Responsible filled on create
- **WHEN** заявка создана и согласована
- **THEN** ответственный заполнен текущим пользователем и недоступен для изменения

#### Scenario: Several sections in one request
- **WHEN** способ указания «По разделам», в таблице две строки с разными разделами
- **THEN** отсечка записана по обоим разделам (общая дата раздела)

#### Scenario: Sections and objects like typical form
- **WHEN** способ указания «По разделам и объектам», в таблице строки с разными разделами и объектами
- **THEN** отсечка записана по каждой паре раздел–объект

#### Scenario: Mixed object types in one request
- **WHEN** согласована заявка со смешанной ТЧ: организация, касса, склад
- **THEN** отсечка записана по всем трём объектам; по истечении срока все три границы возвращены

#### Scenario: Detailed opening copies parent set
- **WHEN** согласована заявка на конкретный объект (касса, организация) пользователю без личных настроек
- **THEN** в типовом РС сразу есть отсечка по заявке и полный набор родителя (группа или «для всех»); прочие объекты и разделы запрещены как до заявки

#### Scenario: Early close drops inherited parent immediately
- **WHEN** по заявке с детальным открытием выполнено досрочное закрытие, других детальных настроек и открытий у адресата нет
- **THEN** унаследованный набор родителя удалён сразу, без ожидания задания; поиск БСП снова идёт по группе / «для всех»

#### Scenario: Organization is mandatory on request
- **WHEN** пользователь записывает заявку без организации
- **THEN** запись отклоняется

#### Scenario: Request without detail role writes addressee general date
- **WHEN** пользователь без роли `нп_УказаниеРазделовИОбъектовЗаявки` записывает заявку с организацией и пустой таблицей
- **THEN** документ записывается; после согласования в типовой РС одна запись: указанный адресат, пустой раздел, пустой объект

#### Scenario: Request section shows documents of that section
- **WHEN** пользователь с ролью детализации выбирает раздел в строке заявки
- **THEN** справа от раздела видно информационное поле со списком документов этого раздела

#### Scenario: Section then object of that section type
- **WHEN** пользователь с ролью детализации выбирает раздел «Банк»
- **THEN** колонка объекта с заголовком «Банковский счет» и типом `БанковскиеСчетаОрганизаций` доступна; рядом с разделом поле организации не показывается

#### Scenario: Mixed section rows keep object column
- **WHEN** в таблице есть строка «Банк» со счётом и строка «Учет по МСФО» без объекта, пользователь встаёт на МСФО
- **THEN** колонка объекта остаётся видимой; ячейка текущей строки только просмотр, значение в строке Банк не пропадает

#### Scenario: Early close stays enabled after Document Management link
- **WHEN** заявка связана с ДО и у неё есть действующее состояние открытого периода
- **THEN** поля только просмотр, а команда «Закрыть период досрочно» доступна полноправному пользователю

### Requirement: Print form for Document Management
Система SHALL предоставлять штатную печатную форму БСП документа `нп_ЗаявкаНаОткрытиеПериода` (команда `ЗаявкаНаОткрытиеПериода`, макет `ПФ_MXL_ЗаявкаНаОткрытиеПериода`) с основными сведениями заявки: номер, дата, пользователь/группа, организация, период с, срок K, причина, ответственный, строки раздела и объекта. Строки «Открывается» в шапке MUST NOT быть: состав уже виден в таблице. Пустая пара раздел+объект MUST печататься в таблице как «все разделы и объекты». Форма MUST быть в списке печатных форм объекта для правила интеграции ДО 3, чтобы согласующие видели сведения файлом, без переноса всех реквизитов и табличных частей в документ ДО.

#### Scenario: Print command is available for Document Management
- **WHEN** в правиле интеграции ДО 3 открывают список печатных форм объекта `нп_ЗаявкаНаОткрытиеПериода`
- **THEN** в списке есть команда `ЗаявкаНаОткрытиеПериода` («Заявка на открытие периода»)

#### Scenario: Print form shows addressee general date
- **WHEN** печатают заявку с пустой таблицей и пустым разделом шапки
- **THEN** в шапке нет строки «Открывается»; в таблице — «все разделы и объекты»

#### Scenario: Print form wording is plain for approvers
- **WHEN** печатают заявку с заполненными строками таблицы разделов
- **THEN** шапка без «Открывается» и без «Указывать»; состав виден в таблице разделов и объектов

### Requirement: Seamless Document Management approval
Согласование SHALL выполняться штатными средствами бесшовной интеграции с 1С:Документооборотом 3 (`ИнтеграцияС1СДокументооборот`, `ОбъектыИнтегрированныеС1СДокументооборотом`, `СостоянияСогласованияВДокументообороте`). Документ MUST входить в определяемые типы `ИнтеграцияС1СДокументооборотВсеСсылкиПереопределяемый` (`DocumentRef`) и `ИнтеграцияС1СДокументооборотДокументыОбъектыПереопределяемый` (`DocumentObject`), иначе его нет в списке объектов правил интеграции. Вид документа, шаблон процесса и состав согласующих настраиваются в ДО и в объём разработки не входят.

Пока заявка не согласована, типовой регистр MUST NOT изменяться. Реакция на изменение состояния MUST быть обработчиком `ПриИзмененииСостоянияСогласования`, а не периодическим опросом.

#### Scenario: Request appears in Document Management integration rules
- **WHEN** пользователь создаёт правило интеграции ДО 3 и выбирает тип объекта ИС
- **THEN** в списке документов есть `нп_ЗаявкаНаОткрытиеПериода`

После появления связи с ДО (ещё до прогрузки `НаСогласовании` в ERP) и в состояниях `НаСогласовании` / `Согласован` изменение документа запрещается: поля формы только просмотр, `ПередЗаписью` отклоняет запись. Это то же защищённое окно, что у контроля проведения: связь есть и состояние ≠ `НеСогласован`. После `НеСогласован` заявку снова можно править. Для изменения параметров согласованной заявки открытый период закрывается досрочно и создаётся новая заявка. Пометка на удаление и отмена проведения запрещены, пока открытый период действует.

Датой согласования считается дата состояния `Согласован` из ДО. День согласования — первый день срока K. Дата окончания действия = дата согласования + K − 1 день (включительно).

Если ДО недоступен, заявка остаётся в текущем состоянии, типовой регистр не изменяется, ошибка пишется в журнал регистрации.

#### Scenario: Unapproved request does not write typical register
- **WHEN** заявка создана и ещё не согласована
- **THEN** типовой регистр не изменён

#### Scenario: Approved document cannot change cutoff
- **WHEN** пользователь пытается изменить «Период с» в согласованном документе
- **THEN** изменение отклонено, отсечка в типовом регистре не изменилась

#### Scenario: Pending approval cannot change request
- **WHEN** заявка уже связана с ДО (статус в ERP ещё пустой или `НаСогласовании`) и пользователь меняет «Период с», объекты или «кому»
- **THEN** изменение отклонено; после `НеСогласован` те же поля снова доступны

#### Scenario: Document Management unavailable
- **WHEN** 1С:Документооборот недоступен в момент отправки или получения состояния
- **THEN** заявка остаётся в текущем состоянии, типовой регистр не изменяется, ошибка фиксируется в журнале регистрации

### Requirement: Cutoff write after approval
После перехода в `Согласован` система SHALL по каждой строке ТЧ записать в типовой РС отсечку «Период с минус 1 день» (конец дня границы) по объектам и разделу документа, для пользователя/группы из реквизита «Пользователь».

Прежнее значение даты запрета по каждой изменяемой комбинации сохраняется в `нп_СостояниеОткрытыхПериодов` до его перезаписи. Пустое `ДатаЗапретаДоОткрытия` означает, что записи в типовом РС не было.

Пока запись регистра состояния действует, автоматическая установка эту комбинацию не перезаписывает.

#### Scenario: Approved request on 20.08.2026
- **WHEN** заявка согласована 20.08.2026, «Период с» = 01.07.2026, K=3
- **THEN** в типовом регистре отсечка 30.06.2026; в регистре состояния сохранено прежнее значение; дата окончания действия — 22.08.2026

#### Scenario: Job does not overwrite while period is open
- **WHEN** задание запускается 21.08 и 22.08 при действующем открытом периоде
- **THEN** отсечка не перезаписывается

#### Scenario: Write inside temporarily opened period succeeds
- **WHEN** пользователь записывает документ с датой внутри временно открытого периода
- **THEN** документ записывается

### Requirement: Restore boundary after K days
Возврат границы SHALL выполняться заданием `нп_СдвигДатЗапретаИзменения` независимо от того, включена ли автоматическая установка по данному объекту.

Для записей состояния с истёкшей датой окончания действия:

1. в типовой РС возвращается `ДатаЗапретаДоОткрытия`; если оно не заполнено — запись типового регистра удаляется;
2. запись регистра состояния удаляется;
3. далее, если есть включённая настройка, применяется «текущая дата минус N».

#### Scenario: Restore then auto-shift
- **WHEN** K=3, согласование 20.08.2026, задание запускается 23.08.2026
- **THEN** возвращено прежнее значение, запись состояния удалена, затем применено «текущая дата минус N» при наличии настройки

#### Scenario: Restore without auto-shift settings
- **WHEN** согласована заявка с заполненным пользователем по объекту без настроек автоматической установки, K=3 (сценарий приёмки 12 заявки ERP.2026.14)
- **THEN** отсечка записана для указанного в документе пользователя (не «для всех»); по истечении срока граница возвращена к прежнему значению (или запись типового РС удалена, если прежнего значения не было)

### Requirement: Early close and overlapping requests
Команда «Закрыть период досрочно» на форме документа SHALL быть доступна пользователю с полными правами. Результат — как при истечении срока K (немедленный возврат, удаление состояния). Прямое исправление типового регистра вручную при действующем состоянии MUST NOT рекомендоваться: запись состояния иначе заблокирует автоустановку.

Две согласованные заявки по одной комбинации «объект — раздел — пользователь» с пересекающимися сроками: применяется наиболее ранняя отсечка; дата окончания действия — наиболее поздняя из двух; `ДатаЗапретаДоОткрытия` сохраняется только при первом открытии и последующими заявками не перезаписывается.

Новая согласованная заявка взамен ошибочной обрабатывается как новое открытие: срок K отсчитывается от даты согласования новой заявки.

Пометка на удаление и отмена проведения запрещены, пока открытый период действует; сначала выполняется досрочное закрытие.

#### Scenario: Early close
- **WHEN** пользователь с полными правами выполняет «Закрыть период досрочно» при действующем открытом периоде
- **THEN** прежнее значение возвращено немедленно, запись состояния удалена, дальнейшие запуски задания применяют настройки автоустановки

#### Scenario: Two overlapping requests
- **WHEN** две заявки по одной организации: отсечки 30.06 и 31.05, сроки перекрываются
- **THEN** действует 31.05; дата окончания — наиболее поздняя; прежнее значение не затёрто

#### Scenario: Deletion blocked while period is open
- **WHEN** пользователь помечает на удаление или отменяет проведение документа при действующем открытом периоде
- **THEN** действие запрещено; требуется сначала досрочное закрытие
