## Context

Заявка **ERP.2026.14**, редакция 2 от 20.08.2026: автоматическая установка дат запрета «сегодня минус N», заявка на временное открытие периода с бесшовным согласованием в 1С:Документообороте 3, отчёт с источником записей.

Среда (из заявки): ERP УХ **3.2.8.26**, БСП **3.1.11.466**, 1С:Документооборот КОРП **3.0.21.3**. Дамп в репозитории — УХ 3.2.8.25; расхождение минорное, API БСП дат запрета совпадает.

Типовой контур сегодня:

- Хранение: РС `ДатыЗапретаИзменения` (измерения `Раздел`, `Объект`, `Пользователь`; ресурс `ДатаЗапрета` — тип **Дата без времени**; реквизиты `ОписаниеДатыЗапрета`, `Комментарий`).
- Проверка: подписки БСП `ПередЗаписью` → `ДатыЗапретаИзменения.ИзменениеЗапрещено`. Сравнение: `РезультатПоиска.ДатаЗапрета < Данные.Дата` — документ **в день границы запрещён**. Это согласуется с нормативной таблицей заявки (запись «15.08.2026 23:59:59» в типовом ресурсе — календарная дата 15.08.2026).
- Поиск (два независимых этапа, `ДатыЗапретаИзмененияСлужебный.НайденЗапретИзмененияДанных`):
  1. Адресат: конкретный пользователь → группа (порядок: `Комментарий` УБЫВ, затем наименование группы УБЫВ) → `Перечисление.ВидыНазначенияДатЗапрета.ДляВсехПользователей`. Наборы адресатов взаимоисключающие.
  2. Внутри адресата: раздел+объект → раздел+«любой объект» (`Объект = Раздел`) → пустой раздел + пустой объект (общая дата адресата).
- Разделы заполняются в `ДатыЗапретаИзмененияПереопределяемый.ПриЗаполненииРазделовДатЗапретаИзменения`. УХ дополнительно добавляет раздел `УчетПоМСФО` (`МСФОБСПУХ`, тип объекта — организация, как у «Продажи»). По решению заказчика раздел входит в разворачивание наравне с «Продажи».
- Бесшовка ДО 3 уже используется контролем проведения (`Extensions/нп_КонтрольПроведенияПоДО`). Точка расширения: `ИнтеграцияС1СДокументооборотБазоваяФункциональностьПереопределяемый.ПриИзмененииСостоянияСогласования`.
- Формы ТН на типовом РС (`тн_УстановитьДатуЗапретаДляСпискаОрганизаций`, `тн_ИзменитьДатыЗапретаПоОрганизации`) и лаунчер `нп_ОткрытиеДатЗапретаИзменения` не трогаем.

Код — **отдельное** расширение `нп_ДатыЗапретаИзменения` (префикс `нп_`, purpose Customization). После приёмки на тесте объекты переносятся в `uhnp.НП`, отдельное расширение снимается. В репозитории: `Extensions/нп_ДатыЗапретаИзменения/`.

## Goals / Non-Goals

**Goals:**

- Скользящая абсолютная граница «сегодня минус N» по закрытому перечню разделов и типов объектов.
- Согласованная заявка временно открывает период на K дней с гарантированным возвратом, в том числе без настроек автоустановки.
- Отчёт показывает, откуда взялась каждая запись типового РС.
- Типовая проверка при записи объектов не меняется.

**Non-Goals:**

- Новый относительный вариант БСП в `ОписаниеДатыЗапрета`.
- «Дырка» в середине закрытого диапазона (одной датой БСП нельзя).
- Разворачивание настройки по всем элементам справочника (кассам, складам, счетам).
- Правки расширения ТН, типовых подписок, лаунчера типовой формы.
- Настройка вида документа / маршрута в ДО 3 (делается до приёмки).
- История изменений и согласование самих настроек автоустановки.
- Пересчёт по часовым поясам организаций.

## Decisions

### 1. Писать в типовой РС в каноническом виде БСП

**Решение:**

| Смысл заявки | Что пишем в типовой РС |
|---|---|
| «для всех пользователей» | `Пользователь = Перечисление.ВидыНазначенияДатЗапрета.ДляВсехПользователей` (не пустая ссылка) |
| «общая дата по разделу» (нет конкретного элемента справочника) | `Объект = Раздел` (ссылка ПВХ), не пустой объект |
| «общая дата адресата» (пустой раздел и объект) | `Раздел` и `Объект` = пустая ссылка ПВХ. Допускается и в настройках, и в заявке. В заявке пользователь/группа **обязательны**, «для всех» нельзя |
| конкретный объект + раздел | как есть |
| конкретный объект, раздел пуст | N записей: каждый допустимый раздел + этот объект |

**Почему:** поиск БСП не смотрит «заполненный раздел + пустой объект». «Любой объект раздела» — это `Объект = Раздел`. «Для всех» — значение перечисления, не пустое измерение. Формулировка заявки «незаполненный объект» читается как «без элемента справочника».

**Альтернатива:** писать пустой объект буквально — отклонена: записи не будут находиться проверкой.

### 2. Пустой объект + пустой раздел: и в настройках, и в заявке

**Решение:** пустая пара — общая дата адресата (одна запись типового РС с пустыми разделом и объектом). Допускается в регистре настроек (таблица 2.1.2) и в заявке на открытие периода.

В заявке обязателен пользователь или группа: нельзя не указать адресата и нельзя открыть период «для всех пользователей». Пустые объект и раздел при заполненном адресате открывают общую дату **этого** адресата (поиск БСП сначала выбирает адресата, записи «для всех» к нему не подмешиваются).

**Почему:** это штатный смысл типовой формы. Ограничение «не для всей базы» закрывается обязательным пользователем, а не требованием указать раздел.

### 3. Закрытый перечень разделов — таблица заявки плюс `УчетПоМСФО`

**Решение:** разворачивание «объект заполнен, раздел пуст» использует таблицу 2.1.2 заявки **и** раздел УХ `УчетПоМСФО` (тип объекта — организация, как у «Продажи»). Итого для организации: 18 разделов. Касса / склад / банк / бюджетирование / планирование — без изменений.

**Почему:** заказчик 27.08.2026: «аналогично как раздел Продажи». В таблице заявки 2.1.2 раздела нет, потому что анализ шёл по `ДатыЗапретаИзмененияПереопределяемый` без вызова `МСФОБСПУХ`.

### 4. Дата в типовом ресурсе — тип Дата

**Решение:** записывать календарную дату границы (`НачалоДня(ТекущаяДатаСеанса() - N * 86400)` с поправкой на тип Дата). Не DateTime 23:59:59 — ресурс регистра `ЧастиДаты.Дата`. Смысл «конец дня» обеспечивает сравнение БСП `<=` по дате без времени.

### 5. Комментарий записей по группам

**Решение:** при записи типового РС по группе пользователей `Комментарий = "нп_авто|" + Формат(N, "ЧЦ=5; ЧВН=")` (например `нп_авто|00030`). Среди групп БСП берёт первую по `Комментарий` УБЫВ — большее N (более ранняя граница) побеждает. Записи не по группам: `Комментарий = "нп_авто"`.

**Почему:** заявка требует осознанно управлять полем; иначе порядок групп недетерминирован (наименование УБЫВ).

### 5а. Автозаписи актуализировать, ручные не трогать

**Решение:** задание пишет и удаляет только записи с комментарием `нп_авто` / `нп_авто|NNNNN`. Ручная запись типовой формы (другой или пустой комментарий) не перезаписывается и не удаляется. После смены или отключения настройки устаревшие автозаписи снимаются, чтобы типовой РС не расходился с регистром настроек. Типовую форму не используют для той же политики, что настройки; вручную — только исключения.

**Почему:** две параллельные админские поверхности забывают синхронизировать. Источник политики — наш регистр настроек плюс согласованные заявки; ручной ввод в типовой форме — явное исключение.

### 6. Регистр состояния, а не чтение заявок заданием

**Решение:** после `Согласован` обработчик сразу пишет отсечку и строку `нп_СостояниеОткрытыхПериодов`. Задание смотрит только регистр состояния (истёкшие) и настройки. Документ после согласования неизменяем.

**Почему:** заявка требует обработчик события, не опрос; прежнее значение нельзя надёжно восстановить из документа.

### 7. Пересечение заявок

**Решение:** ключ состояния = объект + раздел + пользователь типового РС (после разворачивания). При второй согласованной заявке: `ДатаЗапрета` типового РС = мин(текущая отсечка, новая отсечка); `ДатаОкончанияДействия` = макс; `ДатаЗапретаДоОткрытия` и `ЗаявкаНаОткрытиеПериода` первой заявки не затираются (заявка-основание остаётся первой; в отчёте для открытого периода можно дополнительно показать последнюю заявку в комментарии, если понадобится — в первой очереди достаточно первой как «кто открыл исходную границу»).

Уточнение для отчёта: источник «временно открытый период» ссылается на заявку из регистра состояния (первая). Перекрывающая вторая заявка в отчёте **не** выводится (заказчик 27.08.2026). Она видна в журнале и в списке документов.

### 8. Обработчик согласования — расширение типового модуля

**Решение:** в пакете расширения переопределить `ИнтеграцияС1СДокументооборотБазоваяФункциональностьПереопределяемый.ПриИзмененииСостоянияСогласования` (`&После`): если предмет — `нп_ЗаявкаНаОткрытиеПериода` и состояние `Согласован` — открыть период. Не ходить в веб-сервис из задания.

**Почему:** тот же контур, что у зарплатных документов и УХ-заявок в типовом модуле.

### 9. Запись типового РС с отключенной проверкой

**Решение:** вокруг набора: `ДатыЗапретаИзменения.ОтключитьПроверкуДатЗапрета(Истина)` + привилегированный режим; затем `ОбновитьВерсиюДатЗапретаИзменения()`. Иначе запись границы может быть запрещена собственной же датой.

### 10. Права на заявку — без полных прав

**Решение:** заполнить и отправить заявку на открытие периода можно **без полных прав**. Отдельный профиль бухгалтерии и отдельные роли «только заявка» не создаём.

| Действие | Права |
|---|---|
| Создать / заполнить / записать заявку, открыть отчёт | роль `нп_БазовыеПраваДатЗапрета` (в этом расширении) |
| Отправить на согласование в ДО | типовые права бесшовной интеграции ДО 3 |
| Регистр настроек автоустановки, константа уведомлений, задание | полные права |
| «Закрыть период досрочно» | полные права (ИТ) |

`нп_БазовыеПраваДатЗапрета` в этом расширении: документ заявки (чтение/добавление/изменение), отчёт, чтение регистра состояния; **без** регистра настроек и **без** константы уведомлений. Имя временно отличается от `нп_БазовыеПрава` в НП (конфликт при совместной загрузке). После переноса в `uhnp.НП` права вливаются в роль `нп_БазовыеПрава`.

**Почему:** заявка 2.1.1 прямо отделяет регистр настроек (только полные права) от объектов заявки (`нп_БазовыеПраваДатЗапрета`). Пользователь узнаёт о закрытом периоде из типового сообщения при записи, не из регистра настроек.

### 11. Уведомления об ошибках задания

**Решение:** константа `нп_ПолучателиУведомленийСдвигаДатЗапрета` (строка: адреса через `;`) **и форма константы** для заполнения без конфигуратора. Отправка через `РаботаСПочтовымиСообщениями`. Если почта не настроена или константа пуста — только журнал регистрации (событие `нп_СдвигДатЗапретаИзменения`). Форма константы доступна пользователю с полными правами; в командный интерфейс подсистемы.

### 12. Отдельное расширение, затем перенос в НП

**Решение:** вся доработка живёт в отдельном расширении `нп_ДатыЗапретаИзменения` (Customization, префикс `нп_`). Исходники: `Extensions/нп_ДатыЗапретаИзменения/`. Дамп `uhnp/` и `uhnp.НП` на этапе разработки **не** меняем. После теста объекты переносятся в расширение НП, отдельное расширение снимается с ИБ.

**Почему:** заказчик 27.08.2026: сначала отдельное расширение, после теста — в НП. Префикс `нп_` с первого коммита, чтобы перенос был механическим.

### 13. Отдельная подсистема

**Решение:** все новые объекты входят в подсистему `нп_ДатыЗапретаИзменения` (`IncludeInCommandInterface = true`): настройки, константа и её форма, документ заявки, отчёт, задание. Служебный регистр состояния в командный интерфейс не выводим, но в состав подсистемы включаем.

### 14. Печатная форма заявки для согласования в ДО

**Решение:** штатная печатная форма БСП на документе (`ДобавитьКомандыПечати` / `Печать` в менеджере, идентификатор `ЗаявкаНаОткрытиеПериода`, макет `ПФ_MXL_ЗаявкаНаОткрытиеПериода`). На форме нет своей команды печати и нет заимствованных общих команд ДО: подменю печати, файлы и команды бесшовки добавляются программно (`ПодключаемыеКоманды`, `РаботаСФайлами.ПриСозданииНаСервере`, `ИнтеграцияС1СДокументооборотБазоваяФункциональность.ПриСозданииНаСервере`), как в типовых документах. Документ регистрируется в `УправлениеПечатьюПереопределяемый.ПриОпределенииНастроекПечати` (`&После`), иначе БИД не видит команды печати у нового объекта расширения. Менеджерная `Печать()` пишет PDF в присоединенные файлы. В правиле интеграции ДО 3 присоединять эту форму файлом; все реквизиты и ТЧ в документ ДО не маппить. Состав печати — шапка (номер, дата, кому, период с, K, способ, причина, ответственный) и строки раздел/объект; пустая пара — «все разделы / общая дата адресата».

**Почему:** согласующим в ДО нужны основные сведения заявки ЕРП, без дублирования структуры документа.

## Risks / Trade-offs

- **[Риск] Ручная запись типовой формы по той же комбинации, что автонастройка** → задание её не трогает; БСП может взять ручную. Не вести одну политику в двух формах; отчёт помечает такие записи как «вручную».
- **[Риск] Общая дата адресата в типовом РС перекрывает детальные записи того же адресата** → сценарий 7г; инструкция администратору перед первым включением; отчёт помечает такие записи как «вручную».
- **[Риск] Таблица заявки 2.1.2 без `УчетПоМСФО`** → согласовано с заказчиком 27.08.2026: раздел входит как «Продажи»; при обновлении релиза сверить, что тип объекта раздела по-прежнему организация.
- **[Риск] ФО «по разделам / объектам / пользователям» выключены** → записи не применяются; проверка при внедрении, доработка ФО не меняет.
- **[Риск] Открытие июля открывает всё после отсечки, включая август** → ограничение БСП; текст на форме заявки.
- **[Риск] Маршрут ДО не настроен** → заявка не согласуется, даты не меняются (безопасный отказ).
- **[Риск] Увеличение N открывает период без заявки** → допустимо заявкой: настройки ведёт полноправный; факт — в журнале регистрации.
- **[Риск] Несколько групп с одинаковым N** → порядок по наименованию группы; редко; при необходимости править `Комментарий` вручную.
- **[Риск] Расхождение 3.2.8.25 дампа и 3.2.8.26 заявки** → сверить перечень разделов на рабочей базе перед приёмкой.

## Migration Plan

1. Собрать `.cfe` отдельного расширения `нп_ДатыЗапретаИзменения` и загрузить в тестовую ИБ (рядом с НП, не внутрь НП).
2. Включить ФО дат запрета по разделам/объектам/пользователям, если нужны детальные записи.
3. Заполнить константу получателей уведомлений формой константы.
4. На тестовой копии: заполнить настройки, сверить с текущим типовым РС **до** включения задания (в том числе общие даты адресатов).
5. Включить задание по расписанию 23:00.
6. В ДО 3 завести вид документа и правило интеграции для `нп_ЗаявкаНаОткрытиеПериода` (документ включён в определяемые типы БИД `ВсеСсылки` и `ДокументыОбъекты`). В правиле присоединить печатную форму «Заявка на открытие периода»; все реквизиты и табличные части в документ ДО не переносить.
7. После приёмки: перенести объекты в `uhnp.НП`, снять отдельное расширение; права `нп_БазовыеПраваДатЗапрета` влить в `нп_БазовыеПрава`.
8. Откат на этапе отдельного расширения: снять расширение; записи типового РС остаются последними абсолютными датами.
