## Context

Заявка **ERP.2026.14**. Уточнения заказчика после первой реализации: даты запрета **всегда в разрезе организации**; для групп (бухгалтерия, кладовщики) нужны **типовые относительные даты** БСП вместе со скользящим окном; в заявке организация в шапке; раздел и объект — только у новой роли, с каскадом «сначала раздел»; кнопка «Закрыть период досрочно» не должна гаснуть после связи с ДО.

Среда: ERP УХ **3.2.8.26**, БСП **3.1.11.466**, ДО КОРП **3.0.21.3**. Код — отдельное расширение `нп_ДатыЗапретаИзменения`. Типовую проверку `ПередЗаписью` не меняем: пишем только в РС `ДатыЗапретаИзменения`.

Типовой поиск БСП без изменений:

1. Адресат: пользователь → группа (`Комментарий` УБЫВ) → «для всех пользователей». Наборы взаимоисключающие.
2. Внутри адресата: раздел+объект → раздел+«любой объект» (`Объект = Раздел`) → пустой раздел + пустой объект.

Относительные варианты БСП (`КонецПрошлогоМесяца` + дни разрешения и т.п.) считаются так: пока не истекла отсрочка, действует **предыдущий** период (для «конец прошлого месяца» + 5 дней до 5 числа текущего месяца граница — конец позапрошлого месяца; с 6-го — конец прошлого).

## Goals / Non-Goals

**Goals:**

- Автоустановка границы всегда по организации, для пользователя / группы / «для всех».
- Два правила расчёта, в том числе вместе: скользящее «сегодня минус N» и относительная дата как в типовой форме.
- Заявка на временное открытие с организацией в шапке и согласованием в ДО 3.
- Раздел и объект в заявке — только роль детализации; каскад раздел → объект своего типа.
- «Закрыть период досрочно» доступна после связи с ДО.
- Отчёт с источником записи. Типовая проверка не меняется.

**Non-Goals:**

- Писать `ОписаниеДатыЗапрета` в типовой РС (туда идёт уже посчитанная абсолютная дата).
- «Дырка» в середине закрытого периода.
- Разворачивание настройки на все кассы / склады / счета организации.
- Автонастройки, где объект — касса, склад, счёт или сценарий.
- Правки ТН, типовых подписок, лаунчера типовой формы.
- Настройка вида документа / маршрута в ДО 3.
- История и согласование самих настроек.

## Decisions

### 1. Автоустановка — по организации (что это значит)

Типовой регистр ищет дату **по разделу документа и по объекту этого раздела**, не «просто по организации».

Когда пользователь записывает документ, БСП берёт раздел и объект из самого документа:

| Раздел | Какой объект смотрит проверка | Пример документа |
|---|---|---|
| Продажи, закупки, бухучёт, МСФО и ещё 14 таких | организация из документа | реализация, поступление |
| Банк | банковский счёт организации | поступление / списание безналичных |
| Касса | касса | ПКО, РКО |
| Складские операции | склад | ордер на складе |
| Бюджетирование / планирование | сценарий | бюджет, план |

Поэтому запись в типовом РС «раздел Банк, объект = организация Альфа» **на списание со счёта Альфы не действует**: проверка ищет «Банк + этот счёт» (или «Банк + любой объект раздела»), а не «Банк + Альфа».

**Решение для автоустановки:** в настройке обязательна организация. Задание пишет в типовой РС только те разделы, у которых объект как раз организация (18 разделов: продажи, бухучёт, МСФО, …). Кассу, склад, счёт и сценарий в настройке больше не выбираем — иначе пришлось бы либо писать бесполезную пару «Банк + организация», либо снова вести даты по каждому счёту/кассе.

Закрыть банк или кассу точечно можно заявкой с ролью детализации (там как раз появляется объект своего типа) или вручную в типовой форме.

| Раздел в настройке | Что пишем в типовой РС |
|---|---|
| Пустой | 18 организационных разделов, объект = эта организация |
| Один из 18 организационных | этот раздел + эта организация |
| Касса / Банк / Склад / Бюджетирование / Планирование | настройку не принимаем |

Пустая пара «нет объекта и нет раздела» больше не используется. Пустой пользователь в настройке по-прежнему значит «для всех пользователей».

### 2. Способ расчёта: скользящее / относительное / оба

**Решение:** ресурс `СпособРасчета` (`нп_СпособыРасчетаДатыЗапрета`):

| Способ | Что задают | Дата в типовой РС |
|---|---|---|
| Скользящее окно | N (`ЧислоДней`) | `сегодня − N` (нормативная таблица заявки, N включая сегодня) |
| Относительная дата | `ОписаниеДатыЗапрета` + `КоличествоДнейРазрешения` | как типовая форма БСП |
| Комбинированная | и N, и относительное правило | **максимум** двух дат (более поздняя = строже) |

В типовой РС `ОписаниеДатыЗапрета` оставляем пустым: задание каждую ночь пересчитывает абсолютную дату. Иначе в одну запись нельзя сложить два типовых описания.

Примеры на 03.09.2026 и 06.09.2026:

| Кому | Правило | 03.09 | 06.09 |
|---|---|---|---|
| Бухгалтеры | конец прошлого месяца + 5 дней | 31.07 (август ещё открыт) | 31.08 (август закрыт) |
| Кладовщики | то же **и** N = 10 | 24.08 (окно 10 дней строже, чем 31.07) | 31.08 (месяц закрыт строже, чем окно 27.08) |

Доступные описания — те же строки БСП: `КонецПрошлогоГода/Квартала/Месяца/Недели`, `ПредыдущийДень`, и при необходимости «текущие» периоды.

**Почему:** бухгалтерии нужен типовой «прошлый месяц со сдвигом»; кладовщикам — он же плюс короткое скользящее окно.

### 3. Заявка: организация в шапке, детализация по роли

**Решение:**

Шапка (все, у кого `нп_БазовыеПраваДатЗапрета`):

- `Организация` — обязательна
- `Пользователь` (кому) — обязателен, не «для всех»
- `ПериодС`, `СрокДействия` (K), `ПричинаОткрытия`, `Ответственный`

Таблица разделов и объектов **скрыта**, если нет роли `нп_УказаниеРазделовИОбъектовЗаявки` (полноправному оставляем). Без роли при записи таблица очищается — подставить раздел через обмен нельзя.

Без таблицы: после согласования отсечка пишется по **всем 18 организационным разделам** этой организации, для указанного адресата.

С ролью: в строке сначала раздел. Потом:

| Тип объекта раздела | Поле объекта |
|---|---|
| Организация (Продажи, Бухучёт, …) | не показывается; в типовой РС объект = организация шапки |
| Касса / Банк / Склад / Сценарий / Сценарий товарного планирования | показывается, тип ограничен разделом, заголовок: «Касса», «Банковский счет», «Склад», «Сценарий», «Сценарий товарного планирования» |
| Нет уточнения | не показывается |

Несколько строк — несколько разделов в одной заявке. Пустой объект у раздела с уточнением = общая дата раздела (`Объект = Раздел` в типовом РС).

Тумблер «Указывать» с формы снимается: он больше не нужен.

Печать: в шапке организация; без таблицы — «по организации (все разделы учёта)»; со строками — раздел и объект понятным текстом.

### 4. «Закрыть период досрочно» после связи с ДО

**Решение:** не ставить `ТолькоПросмотр` на всю форму — платформа гасит команды командной панели, в том числе досрочное закрытие.

Поля блокируются поштучно, запись по-прежнему режет `ПередЗаписью`. Кнопка видна полноправному и **доступна**, пока есть строки `нп_СостояниеОткрытыхПериодов` по этой заявке — и после «Начать обработку», и после `Согласован`.

### 5. Каноническая запись в типовой РС

Без изменений по смыслу БСП, кроме отказа от пустой пары:

| Смысл | Типовой РС |
|---|---|
| Для всех пользователей | `Пользователь = ДляВсехПользователей` |
| Организация, раздел задан | раздел + организация |
| Организация, раздел пуст | 18 записей: каждый орг. раздел + организация |
| Заявка: раздел без уточнения объекта | раздел + организация шапки |
| Заявка: раздел с уточнением, объект пуст | `Объект = Раздел` |
| Заявка: раздел с уточнением, объект задан | раздел + этот объект |

Автозаписи: комментарий `нп_авто` / `нп_авто|00NNN` (для групп; N скользящего окна, иначе дни разрешения). Ручные не трогаем. Открытый период — `нп_открытие`, задание не перезаписывает.

Наследование набора родителя при личной детальной записи **оставляем**: заявка с ролью может открыть одну кассу — без копии родителя у адресата пропадут остальные запреты группы / «для всех». Для обычной заявки «организация, все орг. разделы» это 18 личных записей — родитель копируется, если своей общей даты нет.

### 6. Согласование, состояние, задание, права, отчёт

Без смены контура:

- `&После` `ПриИзмененииСостоянияСогласования` → отсечка «Период с − 1 день», строка состояния.
- Документ нельзя менять с момента связи с ДО, пока состояние ≠ `НеСогласован`.
- Задание 23:00: сначала истёкшие открытия, затем настройки.
- Пересечение заявок: мин. отсечка, макс. окончание, первая заявка-основание.
- Права: заявка и отчёт — `нп_БазовыеПраваДатЗапрета`; настройки и константа — полные права; детализация — новая маркерная роль; досрочное закрытие — полные права.
- Отчёт: авто / открытый период / вручную.

### 7. Что снимаем из прежней модели

- Автонастройки и заявки по кассе / складу / счёту / сценарию как по основному объекту.
- Общую дату адресата (пустые раздел и объект).
- Тумблер «По разделам / по разделам и объектам» на форме заявки.
- Целиком `ТолькоПросмотр` формы заявки.

## Risks / Trade-offs

- **Банк / касса / склад автоустановкой не закрываются** — только организационные разделы. Документы этих разделов смотрят свой объект (счёт, кассу, склад). Закрыть их точечно можно заявкой с ролью детализации или вручную в типовой форме. Если понадобится автоправило «все счета организации» — это отдельное решение (разворачивание справочника мы по-прежнему не делаем).
- **Комбинированное правило строже каждого по отдельности** — это то, что описано для кладовщиков.
- **Открытие июля по-прежнему открывает всё после отсечки** — ограничение одной даты БСП; текст на форме заявки остаётся.
- **Старые тестовые настройки** с кассой / пустой парой после смены модели не загрузятся — на копии заводить заново.

## Что не трогаем

Отдельное расширение → перенос в НП после теста. Подсистема, константа уведомлений, печать+файлы для ДО, определяемые типы БИД, формы ТН, лаунчер типовой формы.
