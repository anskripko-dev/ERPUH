1. Описание проблемы (как есть)

Тема заявки: автоматическая установка дат запрета изменения и заявка на временное открытие периода.

Подсистема / объект 1С: даты запрета изменения (типовой регистр сведений ДатыЗапретаИзменения), расширение НП.

Описание текущего процесса и проблемы

Типовой механизм БСП «Даты запрета изменения» закрывает период: объекты с датой не позднее установленной границы записывать нельзя.

Граница задаётся абсолютной датой — как по организациям, так и по кассам, складам, банковским счетам и сценариям бюджетирования. Эту дату приходится регулярно переносить вручную. Типовые относительные варианты БСП («конец прошлого месяца», «конец прошлого квартала» и аналогичные) не подходят: требуется скользящая граница вида «сегодня минус N дней», которой в типовом перечне вариантов нет.

Отдельного документа для временного открытия уже закрытого периода с согласованием в 1С:Документообороте в типовой конфигурации нет. Сейчас период открывается администратором вручную по устной или почтовой просьбе, факт открытия и срок нигде не фиксируются, обратное закрытие выполняется по памяти.

Типовая проверка даты запрета при записи объектов работает корректно и изменяться не должна.

2. Требования к доработке (как должно быть)

Реализовать в расширении НП:

автоматическую установку даты запрета: скользящее окно «текущая дата минус N дней», типовое относительное описание БСП и комбинированное правило;

документ заявки на временное открытие периода с бесшовным согласованием в 1С:Документообороте;

отчёт по действующим датам запрета с указанием источника каждой записи.

Типовые объекты не изменяются. Взаимодействие с типовым механизмом — только запись в регистр сведений ДатыЗапретаИзменения.

Подтверждено анализом типового кода (функция ПоискДатыЗапрета/НайтиДатуЗапрета, приложение 1): запись типового регистра ищется по конкретному разделу проверяемых данных; если раздел не совпадает ни с одной записью, поиск сразу проваливается в запись «раздел не заполнен, объект не заполнен» — общую дату адресата, минуя любую попытку найти запись «этот объект в любом разделе». Поэтому организация без раздела разворачивается в 18 организационных разделов, а не в одну запись «организация в любом разделе». Появление новых разделов при обновлении конфигурации требует актуализации перечня.

Разворачивание настройки по элементам справочника (по всем кассам, складам, счетам) не выполняется: перечень объектов меняется, а новые элементы иначе остались бы без границы. Требование «одно правило на все объекты раздела» реализуется записью Объект = Раздел. Форма настройки идёт каскадом от первого поля: сначала организация — в списке только организационные разделы; сначала Банк / касса / склад / сценарий — организация скрыта, появляется объект этого раздела.

Работа дат запрета по разделам, объектам и пользователям в типовом механизме включается функциональными опциями. Доработка не изменяет их состояние; при внедрении необходимо проверить, что нужные опции включены, иначе записи с заполненными объектом, разделом или пользователем применяться не будут.

Ограничение объёма: количество записей типового регистра равно числу строк настроек с учётом разворачивания по разделам. Настройки по отдельным кассам, складам и счетам заводятся только там, где граница действительно отличается от общей; массовое заведение по каждому элементу справочника не предполагается.

2.1.4. Взаимодействие с существующими записями

Ручные записи типового регистра (комментарий не начинается с «нп_авто» и не с «нп_открытие») задание не изменяет и не удаляет. Автоматические записи (комментарий «нп_авто» или «нп_авто|NNNNN») актуализируются по текущим включённым настройкам: дата пересчитывается, комбинации, которых больше нет во включённых настройках, удаляются. Записи открытого периода (комментарий «нп_открытие») до истечения срока K не перезаписываются автоустановкой. Параллельно вести ту же политику в типовой форме не следует: ручная запись по той же комбинации останется и по правилам БСП может перекрыть автоустановку, а задание её не исправит. Типовую форму используют только для исключений, которые нельзя выразить настройкой.

Важное следствие: если по пользователю существует ручная запись в типовом регистре, она перекрывает менее детальную запись автоматической установки в силу типовых правил приоритета БСП. Полный алгоритм этого приоритета — в каком порядке типовой механизм учитывает объект, раздел и пользователя при поиске подходящей записи — по результатам тестов на стенде оказался неочевиден: запись с заполненным пользователем (при пустых объекте и разделе) перекрыла запись по конкретному объекту (при пустом пользователе), тогда как запись «для всех пользователей» (все три измерения пусты) запись по конкретному пользователю не перекрывает. Однозначно вывести из этого общий порядок приоритета нельзя.

Полный алгоритм приоритета типового механизма разобран в приложении Б: поиск идёт в два независимых этапа — сначала выбор адресата (конкретный пользователь → группа, приоритет по полю «Комментарий» → «для всех пользователей»), затем, только внутри найденного адресата, поиск по разделу и объекту. Записи одного адресата не перекрывают и не перекрываются записями другого — это разные, взаимоисключающие наборы.

Если настройка задана по группе пользователей, в типовой регистр записывается одна запись с этой группой. Разворачивание группы в записи по каждому пользователю не выполняется. Приоритет при вхождении пользователя в несколько групп определяется полем «Комментарий» записи типового регистра по каждой группе (по убыванию значения) — см. приложение 1, раздел 4.2. При генерации таких записей полем «Комментарий» необходимо управлять осознанно. Следствие для автоустановки: если у пользователя есть только детальные записи (касса, склад и т.п.), типовой поиск больше не смотрит «для всех» и группы. Задание после применения настроек копирует этому адресату полный набор родителя (выигрывающая группа или «для всех») — и пустую пару, и остальные комбинации. Свою пустую пару из регистра настроек, ручную общую дату и действующее открытие не подменяем; если своя общая дата уже есть, детали родителя не копируем. Согласованная заявка с детальной комбинацией копирует набор родителя сразу при открытии; досрочное закрытие снимает его сразу, если не осталось других детальных записей. 2.1.5. Отключение и удаление настройки

При снятии признака «Включено» или удалении записи настройки регламентное задание при ближайшем успешном запуске удаляет соответствующие автоматические записи из типового регистра, включая ранее скопированный набор родителя, если удалили единственную детальную настройку адресата. Ручные записи не затрагиваются. Если настройку изменили так, что разворачивание даёт другой набор комбинаций (например, убрали организацию — вместо 18 записей по разделам остаётся общая дата адресата), устаревшие автозаписи удаляются, актуальные перезаписываются.

Увеличение N сдвигает дату запрета назад и открывает ранее закрытый период без заявки на открытие периода. Это допустимо, поскольку регистр настроек ведёт пользователь с полными правами. Факт изменения фиксируется штатным журналом регистрации; собственная история изменений и согласование настроек в объём заявки не входят.

Изменённая настройка вступает в силу при ближайшем запуске регламентного задания; до этого момента типовой регистр содержит прежнюю дату.

2.1.6. Регламентное задание

Регламентное задание нп_СдвигДатЗапретаИзменения выполняет запись в типовой регистр в привилегированном режиме и от прав интерактивного пользователя не зависит.

Расписание: ежедневно в 23:00.

Задание идемпотентно: повторный запуск в течение суток не меняет результат.

Если задание не выполнялось (база была недоступна), при очередном запуске выполняется обычный расчёт от текущей даты; догоняющие запуски за пропущенные дни не требуются.

Порядок обработки: сначала восстановление истёкших открытых периодов (2.2.5), затем применение настроек.

Ошибка по одной настройке не прерывает обработку остальных. Каждая ошибка записывается в журнал регистрации с указанием объекта, раздела и пользователя.

При наличии ошибок по итогам выполнения отправляется уведомление администраторам ИТ. Список получателей — константа нп_ПолучателиУведомленийСдвигаДатЗапрета и общая форма заполнения; полные права.

Первый запуск после внедрения выполняется в тестовой копии; результат сверяется с текущим состоянием типового регистра до запуска в рабочей базе.

Пустой пользователь в заявке нельзя. На форме и в списке видно статус согласования ДО. Печатная форма «Заявка на открытие периода» без строки «Открывается»: состав уже в таблице.

2.2.2. Согласование

Согласование выполняется штатными средствами бесшовной интеграции с 1С:Документооборотом (ИнтеграцияС1СДокументооборот, ОбъектыИнтегрированныеС1СДокументооборотом, СостоянияСогласованияВДокументообороте). Вид документа, шаблон процесса и состав согласующих настраиваются в 1С:Документообороте и в объём разработки не входят; требуется их настройка до приёмки.

Пока заявка не согласована, типовой регистр не изменяется. Реакция на изменение состояния реализуется обработчиком события изменения состояния согласования, а не периодическим опросом.

После появления связи с ДО (ещё до прогрузки статуса «На согласовании» в ERP) и в состояниях «На согласовании» / «Согласован» изменение документа запрещается: поля только просмотр, запись отклоняется. Это закрывает паузу обмена: нельзя править заявку, пока согласующие смотрят уже отправленные данные. После «Не согласован» заявку снова можно править и отправить повторно. Для изменения параметров согласованной заявки открытый период закрывается досрочно (2.2.6) и создаётся новая заявка. Команда «Закрыть период досрочно» доступна любому пользователю с правами на документ, пока есть действующее состояние.

Датой согласования считается дата состояния «Согласован», полученная из 1С:Документооборота. День согласования считается первым днём срока K.

2.2.3. Действия после согласования

После перехода в состояние «Согласован» по комбинациям заявки выполняется:

В типовой регистр записывается отсечка «Период с минус 1 день» для пользователя или группы из реквизита «Пользователь». Без таблицы — общая дата адресата. Строка организационного раздела — этот раздел и организация шапки. Строка Банк / касса / склад / сценарий — выбранный объект или Объект = Раздел, если объект пуст.

Прежнее значение даты запрета по каждой изменяемой комбинации сохраняется в регистре состояния (2.2.4) до его перезаписи.

Пример: «Период с» = 01.07.2026, отсечка = 30.06.2026 23:59:59.

2.2.5. Возврат границы после истечения срока

Возврат выполняется регламентным заданием нп_СдвигДатЗапретаИзменения и не зависит от того, включена ли автоматическая установка по данному объекту. Это требование критично: без него период, открытый по объекту без настроек автоматической установки, остался бы открытым бессрочно.

При запуске задания обрабатываются записи регистра состояния с истёкшей датой окончания действия.

В типовой регистр возвращается значение из реквизита «ДатаЗапретаДоОткрытия». Если оно не заполнено, запись типового регистра удаляется.

Запись регистра состояния удаляется.

Далее по этой комбинации отрабатывает автоматическая установка, если она включена, и записывает «текущая дата минус N».

Фактически период остаётся открытым до ближайшего запуска задания после истечения срока K. Это допустимо; пользователям сообщается в пояснении на форме документа.

2.2.7. Пояснение на форме документа

На форме размещается постоянно видимый текст: отсечка типового механизма открывает все данные после даты «Период с минус 1 день», а не только тот период, ради которого создана заявка. Дата окончания периода в документе не указывается сознательно, чтобы не создавать у согласующих ложного представления об ограничении открытого интервала сверху.

В пояснении на форме время регламентного задания не указывается. Фактический возврат границы — ночным заданием на следующий день после последнего дня K (или командой «Закрыть период досрочно»).

2.3. Отчёт по действующим датам запрета

Отчёт нп_ДействующиеДатыЗапрета показывает текущее содержимое типового регистра с указанием источника каждой записи:

автоматическая установка (с указанием настройки и N);

временно открытый период (с указанием заявки и даты окончания действия);

установлено вручную — записи типового регистра, не соответствующие ни одной настройке и ни одному открытому периоду.

Для записей временно открытого периода дополнительно выводится ответственный по заявке (первая заявка из регистра состояния; вторая пересекающаяся заявка отдельной строкой не показывается). Колонка описания даты запрета — читаемый текст, как на типовой форме БСП. Отбор по объекту, разделу и пользователю. Отчёт — только полные права, в базовую роль не входит. Нужен для разбора спорных ситуаций и контроля ручных записей, которые задание намеренно не трогает (2.1.4).

3. Экономическое обоснование

Цель доработки: снижение трудозатрат, снижение операционных рисков.

Ожидаемый результат

Абсолютная дата запрета сдвигается автоматически при неизменном N, ручной перенос не требуется.

Разные значения N действуют для разных пользователей, групп пользователей и разделов одного объекта; охвачены все типы объектов дат запрета, а не только организации.

Согласованная заявка временно открывает период на K дней, после чего граница гарантированно возвращается — в том числе по объектам без настроек автоматической установки.

Факт и срок открытия периода фиксируются документом и подтверждаются согласованием в 1С:Документообороте, а не устной договорённостью.

Типовая проверка периода при записи документов и справочников не изменяется.
