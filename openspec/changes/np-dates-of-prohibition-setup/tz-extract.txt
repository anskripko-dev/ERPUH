Исходные данные среды

1. Описание проблемы (как есть)

Тема заявки: автоматическая установка дат запрета изменения и заявка на временное открытие периода.

Подсистема / объект 1С: даты запрета изменения (типовой регистр сведений ДатыЗапретаИзменения), расширение НП.

Описание текущего процесса и проблемы

Типовой механизм БСП «Даты запрета изменения» закрывает период: объекты с датой не позднее установленной границы записывать нельзя.

Граница задаётся абсолютной датой — как по организациям, так и по кассам, складам, банковским счетам и сценариям бюджетирования. Эту дату приходится регулярно переносить вручную. Типовые относительные варианты БСП («конец прошлого месяца», «конец прошлого квартала» и аналогичные) не подходят: требуется скользящая граница вида «сегодня минус N дней», которой в типовом перечне вариантов нет.

Отдельного документа для временного открытия уже закрытого периода с согласованием в 1С:Документообороте в типовой конфигурации нет. Сейчас период открывается администратором вручную по устной или почтовой просьбе, факт открытия и срок нигде не фиксируются, обратное закрытие выполняется по памяти.

Типовая проверка даты запрета при записи объектов работает корректно и изменяться не должна.

2. Требования к доработке (как должно быть)

Реализовать в расширении НП:

автоматическую установку абсолютной даты запрета по правилу «текущая дата минус N дней»;

документ заявки на временное открытие периода с бесшовным согласованием в 1С:Документообороте;

отчёт по действующим датам запрета с указанием источника каждой записи.

Типовые объекты не изменяются. Взаимодействие с типовым механизмом — только запись в регистр сведений ДатыЗапретаИзменения.

2.1. Автоматическая установка даты запрета

2.1.1. Регистр настроек

Настройки ведутся в регистре сведений нп_НастройкиАвтоматическойУстановкиДатЗапрета (независимый, непериодический).

Для одного объекта допускается несколько настроек с разным N: по пользователям или группам пользователей и, при необходимости, по разделам.

Регистр ведёт пользователь с полными правами. Отдельные роли для настроек не создаются. Роль нп_БазовыеПрава даёт доступ только к объектам, необходимым для работы с заявкой на открытие периода; ни чтение, ни запись регистра настроек в неё не входят. Пользователь узнаёт, что период закрыт, из типового сообщения об ошибке при записи и из пояснения на форме заявки (2.2.7), а не из регистра настроек.

2.1.2. Разделы дат запрета

Доработка охватывает все разделы дат запрета, независимо от типа объекта. Перечень разделов и допустимых типов объектов закрытый (по данным анализа модуля ДатыЗапретаИзмененияПереопределяемый используемого релиза):

Пустые объект и раздел вместе означают общую дату «на все случаи» — но только для своего пользователя или группы (приложение 1, разделы 3.3 и 4.1). Настройки по конкретным объектам для того же пользователя ей не мешают: общая дата применяется, только если для проверяемых данных не нашлось более точной записи.

Допустимые сочетания объекта и раздела в настройке:

Подтверждено анализом типового кода (функция ПоискДатыЗапрета/НайтиДатуЗапрета, приложение 1): запись типового регистра ищется по конкретному разделу проверяемых данных; если раздел не совпадает ни с одной записью, поиск сразу проваливается в запись «раздел не заполнен, объект не заполнен» — общую дату адресата, минуя любую попытку найти запись «этот объект в любом разделе». Поэтому настройка по объекту разворачивается в отдельные записи по каждому разделу, допускающему тип этого объекта, и появление новых разделов при обновлении конфигурации требует актуализации перечня.

Разворачивание настройки по элементам справочника (по всем кассам, складам, счетам) не выполняется: перечень объектов меняется, а новые элементы иначе остались бы без границы. Требование «одно правило на все объекты раздела» реализуется записью с незаполненным объектом.

Работа дат запрета по разделам, объектам и пользователям в типовом механизме включается функциональными опциями. Доработка не изменяет их состояние; при внедрении необходимо проверить, что нужные опции включены, иначе записи с заполненными объектом, разделом или пользователем применяться не будут.

Ограничение объёма: количество записей типового регистра равно числу строк настроек с учётом разворачивания по разделам. Настройки по отдельным кассам, складам и счетам заводятся только там, где граница действительно отличается от общей; массовое заведение по каждому элементу справочника не предполагается.

2.1.3. Правило расчёта даты

Регламентное задание нп_СдвигДатЗапретаИзменения записывает в типовой регистр ДатыЗапретаИзменения абсолютную дату, рассчитанную как конец дня даты «текущая дата сеанса минус N дней».

Смысловая трактовка: N — количество последних календарных дней (включая текущий), доступных для редактирования.

Приведённая таблица является нормативной: при расхождении с любым другим текстом заявки верна таблица. Запись конца дня подтверждена на тестовом стенде 22.08.2026: документ, датированный днём границы, не редактируется.

Датой сеанса считается серверная дата сеанса регламентного задания. Пересчёт по часовым поясам организаций не выполняется — серверного времени достаточно.

2.1.4. Взаимодействие с существующими записями

Ручные записи типового регистра (комментарий не начинается с «нп_авто» и не с «нп_открытие») задание не изменяет и не удаляет. Автоматические записи (комментарий «нп_авто» или «нп_авто|NNNNN») актуализируются по текущим включённым настройкам: дата пересчитывается, комбинации, которых больше нет во включённых настройках, удаляются. Записи открытого периода (комментарий «нп_открытие») до истечения срока K не перезаписываются автоустановкой.

Параллельно вести ту же политику в типовой форме не следует: ручная запись по той же комбинации останется и по правилам БСП может перекрыть автоустановку, а задание её не исправит. Типовую форму используют только для исключений, которые нельзя выразить настройкой.

Важное следствие: если по пользователю существует ручная запись в типовом регистре, она перекрывает менее детальную запись автоматической установки в силу типовых правил приоритета БСП. Полный алгоритм этого приоритета — в каком порядке типовой механизм учитывает объект, раздел и пользователя при поиске подходящей записи — по результатам тестов на стенде оказался неочевиден: запись с заполненным пользователем (при пустых объекте и разделе) перекрыла запись по конкретному объекту (при пустом пользователе), тогда как запись «для всех пользователей» (все три измерения пусты) запись по конкретному пользователю не перекрывает. Однозначно вывести из этого общий порядок приоритета нельзя.

Полный алгоритм приоритета типового механизма разобран в приложении Б: поиск идёт в два независимых этапа — сначала выбор адресата (конкретный пользователь → группа, приоритет по полю «Комментарий» → «для всех пользователей»), затем, только внутри найденного адресата, поиск по разделу и объекту. Записи одного адресата не перекрывают и не перекрываются записями другого — это разные, взаимоисключающие наборы.

Следствие для автоустановки: если у пользователя есть только детальные записи (касса, склад и т.п.), типовой поиск больше не смотрит «для всех» и группы. Задание после применения настроек копирует этому адресату полный набор родителя (выигрывающая группа или «для всех») — и пустую пару, и остальные комбинации, например склад группы «Продажи». Свою пустую пару из регистра настроек, ручную общую дату и действующее открытие не подменяем; если своя общая дата уже есть, детали родителя не копируем. Детальная запись остаётся точнее; остальные запреты такие же, как до неё. Кого дополнять, задание берёт из включённых настроек этого запуска: после удаления детальной настройки унаследованный набор родителя снимается тем же запуском, а не следующим.

Если настройка задана по группе пользователей, в типовой регистр записывается одна запись с этой группой. Разворачивание группы в записи по каждому пользователю не выполняется. Приоритет при вхождении пользователя в несколько групп определяется полем «Комментарий» записи типового регистра по каждой группе (по убыванию значения) — см. приложение 1, раздел 4.2. При генерации таких записей полем «Комментарий» необходимо управлять осознанно.

2.1.5. Отключение и удаление настройки

При снятии признака «Включено» или удалении записи настройки регламентное задание при ближайшем успешном запуске удаляет соответствующие автоматические записи из типового регистра, включая ранее скопированный набор родителя, если удалили единственную детальную настройку адресата. Ручные записи не затрагиваются.

Если настройку изменили так, что разворачивание даёт другой набор комбинаций (например, убрали организацию — вместо 18 записей по разделам остаётся общая дата адресата), устаревшие автозаписи удаляются, актуальные перезаписываются.

Увеличение N сдвигает дату запрета назад и открывает ранее закрытый период без заявки на открытие периода. Это допустимо, поскольку регистр настроек ведёт пользователь с полными правами. Факт изменения фиксируется штатным журналом регистрации; собственная история изменений и согласование настроек в объём заявки не входят.

Изменённая настройка вступает в силу при ближайшем запуске регламентного задания; до этого момента типовой регистр содержит прежнюю дату.

2.1.6. Регламентное задание

Регламентное задание нп_СдвигДатЗапретаИзменения выполняет запись в типовой регистр в привилегированном режиме и от прав интерактивного пользователя не зависит.

Расписание: ежедневно в 23:00.

Задание идемпотентно: повторный запуск в течение суток не меняет результат.

Если задание не выполнялось (база была недоступна), при очередном запуске выполняется обычный расчёт от текущей даты; догоняющие запуски за пропущенные дни не требуются.

Порядок обработки: сначала восстановление истёкших открытых периодов (2.2.5), затем применение настроек.

Ошибка по одной настройке не прерывает обработку остальных. Каждая ошибка записывается в журнал регистрации с указанием объекта, раздела и пользователя.

При наличии ошибок по итогам выполнения отправляется уведомление администраторам ИТ (список получателей — константа или регистр настроек уведомлений).

Первый запуск после внедрения выполняется в тестовой копии; результат сверяется с текущим состоянием типового регистра до запуска в рабочей базе.

2.2. Заявка на временное открытие периода

2.2.1. Реквизиты документа

Документ нп_ЗаявкаНаОткрытиеПериода.

2.2.2. Согласование

Согласование выполняется штатными средствами бесшовной интеграции с 1С:Документооборотом (ИнтеграцияС1СДокументооборот, ОбъектыИнтегрированныеС1СДокументооборотом, СостоянияСогласованияВДокументообороте). Вид документа, шаблон процесса и состав согласующих настраиваются в 1С:Документообороте и в объём разработки не входят; требуется их настройка до приёмки.

Пока заявка не согласована, типовой регистр не изменяется. Реакция на изменение состояния реализуется обработчиком события изменения состояния согласования, а не периодическим опросом.

После перехода в состояние «Согласован» изменение документа запрещается штатными средствами интеграции. Это исключает сдвиг отсечки глубже согласованной и перезапуск процесса согласования по уже открытому периоду. Для изменения параметров открытый период закрывается досрочно (2.2.6) и создаётся новая заявка.

Датой согласования считается дата состояния «Согласован», полученная из 1С:Документооборота. День согласования считается первым днём срока K.

2.2.3. Действия после согласования

После перехода в состояние «Согласован» по каждой строке табличной части документа выполняется:

В типовой регистр записывается отсечка «Период с минус 1 день» (конец дня) — по объектам и разделу документа, для пользователя или группы, указанных в реквизите «Пользователь» документа.

Прежнее значение даты запрета по каждой изменяемой комбинации сохраняется в регистре состояния (2.2.4) до его перезаписи.

Пример: «Период с» = 01.07.2026, отсечка = 30.06.2026 23:59:59.

2.2.4. Регистр состояния открытых периодов

Для корректного возврата границы вводится регистр сведений нп_СостояниеОткрытыхПериодов (независимый, непериодический).

Пока запись регистра состояния действует, автоматическая установка эту комбинацию не перезаписывает.

2.2.5. Возврат границы после истечения срока

Возврат выполняется регламентным заданием нп_СдвигДатЗапретаИзменения и не зависит от того, включена ли автоматическая установка по данному объекту. Это требование критично: без него период, открытый по объекту без настроек автоматической установки, остался бы открытым бессрочно.

При запуске задания обрабатываются записи регистра состояния с истёкшей датой окончания действия.

В типовой регистр возвращается значение из реквизита «ДатаЗапретаДоОткрытия». Если оно не заполнено, запись типового регистра удаляется.

Запись регистра состояния удаляется.

Далее по этой комбинации отрабатывает автоматическая установка, если она включена, и записывает «текущая дата минус N».

Фактически период остаётся открытым до ближайшего запуска задания после истечения срока K. Это допустимо; пользователям сообщается в пояснении на форме документа.

2.2.6. Нештатные ситуации

2.2.7. Пояснение на форме документа

На форме размещается постоянно видимый текст: отсечка типового механизма открывает все данные после даты «Период с минус 1 день», а не только тот период, ради которого создана заявка. Дата окончания периода в документе не указывается сознательно, чтобы не создавать у согласующих ложного представления об ограничении открытого интервала сверху.

Дополнительно выводится примечание о том, что фактический возврат границы происходит при ближайшем ночном запуске регламентного задания.

2.3. Отчёт по действующим датам запрета

Отчёт нп_ДействующиеДатыЗапрета показывает текущее содержимое типового регистра с указанием источника каждой записи:

автоматическая установка (с указанием настройки и N);

временно открытый период (с указанием заявки и даты окончания действия);

установлено вручную — записи типового регистра, не соответствующие ни одной настройке и ни одному открытому периоду.

Для записей, возникших из временно открытого периода, дополнительно выводится ответственный по заявке. Отбор по объекту, разделу и пользователю. Отчёт необходим для разбора спорных ситуаций и для контроля ручных записей, которые задание намеренно не трогает (2.1.4).

3. Экономическое обоснование

Цель доработки: снижение трудозатрат, снижение операционных рисков.

Ожидаемый результат

Абсолютная дата запрета сдвигается автоматически при неизменном N, ручной перенос не требуется.

Разные значения N действуют для разных пользователей, групп пользователей и разделов одного объекта; охвачены все типы объектов дат запрета, а не только организации.

Согласованная заявка временно открывает период на K дней, после чего граница гарантированно возвращается — в том числе по объектам без настроек автоматической установки.

Факт и срок открытия периода фиксируются документом и подтверждаются согласованием в 1С:Документообороте, а не устной договорённостью.

Типовая проверка периода при записи документов и справочников не изменяется.

Регистр сведений нп_НастройкиАвтоматическойУстановкиДатЗапрета с формами списка и записи.

Регистр сведений нп_СостояниеОткрытыхПериодов (в командном интерфейсе; записывает задание и обработчик согласования).

Общий модуль нп_ДатыЗапретаИзменения: расчёт даты, запись в типовой регистр, возврат границы.

Регламентное задание нп_СдвигДатЗапретаИзменения: восстановление истёкших открытых периодов, затем применение настроек.

Документ нп_ЗаявкаНаОткрытиеПериода с бесшовной интеграцией 1С:Документооборот, обработчиком изменения состояния согласования и командой досрочного закрытия.

Отчёт нп_ДействующиеДатыЗапрета.

Роль нп_БазовыеПрава дополняется правами на новые объекты расширения; новые роли не создаются.

Типовые подписки проверки даты запрета и формы расширения ТН не изменяются.

Затронутые объекты конфигурации, влияние на другие подсистемы

Расширение НП: новые объекты с префиксом нп_.

Типовой регистр ДатыЗапретаИзменения: только запись и удаление записей по правилам настоящей заявки.

Расширение ТН не затрагивается. Влияние на типовую проверку даты запрета при записи объектов отсутствует.

Инструкция для пользователя

Пользователь с полными правами заполняет регистр нп_НастройкиАвтоматическойУстановкиДатЗапрета и включает регламентное задание.

Пользователь создаёт документ нп_ЗаявкаНаОткрытиеПериода, указывает пользователя или группу, для которых открывается период, и отправляет документ на согласование в 1С:Документооборот. После согласования период открывается автоматически, по истечении срока — закрывается. Изменить согласованный документ нельзя; если параметры оказались неверны или период больше не нужен, следует обратиться в ИТ для досрочного закрытия и создать новую заявку.

Текущее состояние границ и источник каждой записи проверяются отчётом нп_ДействующиеДатыЗапрета.

Перед первым включением автоматической установки по каждому адресату (пользователю, группе или «для всех пользователей») администратор проверяет, нет ли по этому же адресату ранее заведённой вручную записи с пустыми разделом и объектом («общей даты адресата», см. приложение 1, разделы 3.3 и 7) — такая запись сработает для всех разделов, где автоматическая установка не завела запись с точным совпадением, и может дать неожиданный результат.

5. Критерии приёмки

Доработка считается принятой при успешном прохождении всех сценариев. Проверка выполняется на тестовой копии рабочей базы.
