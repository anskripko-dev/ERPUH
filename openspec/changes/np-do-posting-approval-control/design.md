## Context

ERP УХ 3.2.8.25 уже содержит библиотеку интеграции с 1С:Документооборот (БИД):

- формы документов (в т.ч. `ПеремещениеТоваров`) вызывают `ИнтеграцияС1СДокументооборотБазоваяФункциональность.ПриСозданииНаСервере` / `ПередЗаписьюНаСервере`;
- состояние согласования кэшируется в `СостоянияСогласованияВДокументообороте` по ID объекта ДО;
- связь ERP↔ДО — `ОбъектыИнтегрированныеС1СДокументооборотом`;
- API `СогласованВ1СДокументооборот(Ссылка)` читает веб-сервис, при сбое — регистр;
- `ПриИзмененииСостоянияСогласования` синхронизирует реквизиты **ограниченного** списка типов (заказы, договоры, заявки на ДС и т.д.) — **ПеремещениеТоваров туда не входит**;
- реквизит `Статус` перемещения — логистика (`Отгружено`/`Принято`), не согласование.

Кастомизация — в расширении **НП** (`нп_`), не в основной конфигурации и не через пользовательский `Выполнить()` проекта «Обработчики событий» (evh_) для критичного запрета проведения.

## Goals / Non-Goals

**Goals:**

- Универсальный серверный запрет проведения для настроенных типов документов до состояния «Согласован» в ДО
- Настройки без правки кода при подключении нового типа (регистр настроек)
- Источник истины статуса — типовой регистр ДО
- UX: показать состояние согласования на форме подключённого документа
- Пилот: `Документ.ПеремещениеТоваров`
- Роль обхода контроля (заменено отбором участников)
- Защита проведения при существенных изменениях документа в состояниях `НаСогласовании` / `Согласован` (белый список реквизитов; перезапуск обработки ДО 3 по подтверждению)

**Non-Goals:**

- Блокировка **записи без проведения** при изменении защищённых реквизитов (в MVP вопрос и перезапуск — только при проведении)
- Автопроведение документа после согласования в ДО (отдельное решение при необходимости)
- Дублирование статуса в доп. реквизитах БСП / реквизитах объекта как master
- Перенос контроля в evh_ (`Выполнить` в безопасном режиме)
- Согласование через подсистему УХ (`РегистрСостоянийОбъектов`) как основной контур этой задачи
- Правки типовых модулей БИД в основной конфигурации (только чтение/вызовы из расширения)
- Покрытие справочников (только документы с проведением в MVP)

## Decisions

### 1. Размещение в расширении НП

**Решение:** все объекты — в `uhnp.НП` с префиксом `нп_`.

**Почему:** кастомизация холдинга НП; не смешивать с ТН и не править типовую УХ.

### 2. Источник истины статуса — регистр ДО

**Решение:** для контроля проведения читать связку:

`ОбъектыИнтегрированныеС1СДокументооборотом` → `СостоянияСогласованияВДокументообороте.Состояние`

без обязательного веб-вызова на каждое проведение. Веб-API `СогласованВ1СДокументооборот` — только опциональный fallback / ручное обновление UI, не основной путь проведения.

**Почему:** проведение не должно зависеть от доступности ДО; регистр уже обновляется обменом/событиями БИД.

### 3. Настройки по типу метаданных и организации

**Решение:** независимый РС `нп_НастройкиКонтроляПроведенияПоДО`:

| Поле | Назначение |
|---|---|
| Измерение `ПолноеИмяОбъектаМетаданных` | Строка полного имени (`Документ.ПеремещениеТоваров`) |
| Измерение `Организация` | `СправочникСсылка.Организации` — настройка своя для каждой организации |
| `КонтролироватьПроведение` | Булево |
| `ДатаНачалаДействия` | Дата (без времени). Контроль применяется к документам с `Дата` ≥ этой даты |

Текст отказа фиксированный в коде (не ресурс РС): `Проведение запрещено: документ не согласован в 1С:Документооборот (текущее состояние: %1).`, где `%1` — представление состояния из РС / «Нет связи с Документооборотом».

**Поиск настройки:** ключ = полное имя метаданных документа + `Организация` документа (реквизит `Организация`). Если реквизита нет или организация не заполнена, либо записи настройки нет — контроль не применяется.

**Правило при включённом контроле:** если `ДатаНачалаДействия` заполнена и `НачалоДня(Дата документа) < ДатаНачалаДействия` — контроль не применяется (можно проводить без согласования). Иначе проведение разрешено только при состоянии `Согласован` в РС ДО. Нет связи с ДО / нет состояния / `НаСогласовании` / `НеСогласован` → отказ. Отдельной политики «только если есть связь» нет: иначе контроль обходится неотправкой на согласование. Если `ДатаНачалаДействия` пуста — контроль действует на все даты.

**Риск задним числом:** обычный пользователь может обойти контроль, поставив дату документа раньше порога. Порог задавать осознанно; при жёстком режиме — не оставлять дату пустой и ограничивать изменение даты правами/доп. контролем (вне MVP).

**Почему измерение — строка, а не ИОМ:** проще перенос и ручной ввод; совпадает с `Метаданные().ПолноеИмя()`; не зависит от пересоздания `ИдентификаторыОбъектовМетаданных` между ИБ.

**Почему организация в ключе:** разные юрлица могут включать контроль независимо.

**Почему регистр настроек:** новый тип = строки настройки по организациям + правило интеграции в ДО, без `Если ТипЗнч`.

**UX ввода:** формы записи РС настроек и разрешённых реквизитов — режим списка выбора (`СписокВыбора`): документы из `Метаданные.Документы`, реквизиты — шапка + `ТЧ.Реквизит` выбранного типа. Ручной ввод полного имени не нужен.

### 4. Точка контроля — подписка ПередЗаписью

**Решение:** подписка `нп_КонтрольПроведенияПоДОПередЗаписьюДокумента`; источник — набор типов `DocumentObject` (все документы). Состав контролируемых типов задаётся только записями РС настроек. В обработчике — ранний выход, если для `Метаданные().ПолноеИмя()` нет настроек контроля (кэш ПовтИсп). Заимствовать документы в расширение не требуется.

Алгоритм:

1. `ОбменДанными.Загрузка` → выход  
2. Нет активной настройки для пары (тип + организация документа) → выход  
3. Выключены ФО/константы интеграции и согласования через ДО → выход (контроль не мешает, пока ДО не включён)  
4. `РежимЗаписи <> Проведение` → выход (запись и отмена проведения не блокируются в MVP)  
5. Дата документа < `ДатаНачалаДействия` (если дата начала заполнена) → выход  
6. Отбор участников не пройден → выход  
7. Состояние ≠ `Согласован` → `СообщитьПользователю` + `Отказ = Истина`

**Почему:** одна точка на все типы; не править ObjectModule каждого документа.

**Альтернатива отклонена:** только `&После("ПередЗаписью")` на заимствованном модуле перемещения — не масштабируется.

### 5. Статус на форме — проекция из регистра

**Решение:** не хранить master в реквизите/доп. реквизите. На форме:

- реквизит формы `нп_СостояниеСогласованияДО` (строка / перечисление-представление);
- заполнение в `&После` типового `ПриСозданииНаСервере` формы документа (для пилота — форма `ПеремещениеТоваров`; универсально — через заимствование `МодификацияКонфигурацииПереопределяемый.ПриСозданииНаСервере` **или** точечное расширение форм подключённых типов).

**Универсальный путь для форм:** предпочтительно `МодификацияКонфигурацииПереопределяемый` (`&После`), внутри — проверка «есть настройка для типа + организации» и вывод декорации/поля. Формы вне этой точки — вне гарантии UX (серверный запрет всё равно действует).

Опционально: отключить/ограничить команду проведения на клиенте при несогласованном состоянии — только UX; сервер обязателен.

### 6. Не использовать evh_ и доп. реквизиты как основу

**Решение:** критичный запрет — в коде расширения НП. Evh_ допустим позже только как тонкая обёртка вызова `нп_...РазрешеноПроведение`, не как хранилище политики. Доп. реквизит БСП — не использовать в этой change.

### 7. Исключения из контроля

**Решение:** отдельной роли обхода нет. Исключения — отбором участников в настройке (включая/исключая) либо выключением `КонтролироватьПроведение` / даты начала. Полноправие само по себе обход не даёт. Исторические документы с датой раньше `ДатаНачалаДействия` не контролируются.

### 8. Публичный API модуля

```bsl
// Служебный программный интерфейс / программный интерфейс
Функция РазрешеноПроведениеПоСогласованиюДО(СсылкаНаОбъект) Экспорт
Функция СостояниеСогласованияДО(СсылкаНаОбъект) Экспорт // из РС, без веб
Функция НастройкаКонтроля(ПолноеИмя, Организация) Экспорт
Процедура УстановитьНастройкуПоУмолчаниюДляПеремещенияТоваров(Организация, ДатаНачалаДействия = Неопределено) Экспорт
Процедура ПроверитьПередЗаписьюДокумента(Источник, Отказ, РежимЗаписи, РежимПроведения) Экспорт
Процедура ПриСозданииФормыДокумента(Форма) Экспорт // UX статуса
// Пересогласование при существенных изменениях (ДО 3):
Функция ЕстьСущественныеИзмененияДляПересогласования(Источник) Экспорт
Функция ВыполнитьПерезапускОбработкиДО3(СсылкаНаОбъект) Экспорт
Функция ЕстьСущественныеИзмененияДляПересогласования(Источник) Экспорт
```

Устаревший синоним API (если остаётся): `НастройкаКонтроляПоОбъектуМетаданных` — не использовать; только пара (тип + организация).

### 9. Существенные изменения → перезапуск обработки ДО 3

**Контекст:** запись без проведения не блокируется. Вопрос пользователю и вызовы ДО — **только при проведении**.

**Когда применяется:** для пары (тип + организация) включён контроль проведения (и дата ≥ порога, если задана); документ в **защищённом окне**: есть связь в `ОбъектыИнтегрированныеС1СДокументооборотом` и состояние ≠ `НеСогласован` (включая пустое состояние до прихода статуса из обмена, а также `НаСогласовании` / `Согласован`); нет роли обхода.

**Разрешённые реквизиты:** РС `нп_РазрешенныеРеквизитыПриСогласованииДО`:

| Поле | Назначение |
|---|---|
| Измерение `ПолноеИмяОбъектаМетаданных` | Строка (`Документ.ПеремещениеТоваров`) |
| Измерение `Организация` | `СправочникСсылка.Организации` |
| Измерение `ИмяРеквизита` | Строка: реквизит шапки (`Комментарий`) или `ИмяТЧ.ИмяРеквизита` |

Реквизиты из списка можно менять без пересогласования. Остальные отличия объекта от данных в БД (на момент `ПередЗаписью`) — **существенные**.

**Обнаружение изменений:** в `ПередЗаписью` при `Проведение` сравнить `Источник` с значениями из БД по ссылке (`ЗначенияРеквизитовОбъекта` / поэлементно ТЧ). Новые непроведённые (ещё не записанные) объекты без состояния ДО — вне этой ветки. Если документ уже записан с существенными полями, а затем проводится без новых отличий от БД — нужен **маркер** «были существенные изменения после согласования»:

- РС `нп_ПризнакиПересогласованияДО` (измерение — `DocumentRef`; ресурс `ТребуетсяПересогласование` Булево);
- в `ПередЗаписью` при любом режиме записи: если документ в защищённом окне (связь с ДО есть, состояние не `НеСогласован`) и есть существенные отличия от БД → установить признак `Истина` (запись документа при этом не блокируется);
- признак сбрасывать при успешном перезапуске обработки и/или когда состояние снова стало «чистым» после нового согласования (по событию/при следующей проверке, если состояние уже не защищённое — сброс опционально).

Так покрывается сценарий: изменили и записали → потом нажали «Провести».

**Проведение (только сервер, подписка `ПередЗаписью`):**

1. Если требуется пересогласование (признак или существенный diff в этой же записи) → прервать и перезапустить обработку ДО 3 через API БИД (`ПрерватьОбработку` + `ПерезапуститьОбработку`).
2. При ошибке API → `Отказ` с текстом ошибки.
3. При успешном перезапуске → сбросить признак; `Отказ` с сообщением провести после нового `Согласован` (контроль проведения по состоянию сохраняется).
4. Клиентский вопрос и заимствование формы документа не используются.

**Почему не править только РС состояний:** процессы в ДО останутся активными; источник истины процессов — WS ДО 3.

**Почему только при проведении:** по требованию; промежуточные записи для черновиков допустимы, но проведение «по старому согласованию» после существенных правок — нет.

**Обход:** только если настройка неприменима (в т.ч. отбор участников). Полноправие и отдельная роль обхода не используются.

## Risks / Trade-offs

- [Задним числом до порога] → обычный пользователь обходит контроль сменой даты документа; орг. дисциплина / доп. контроль даты вне MVP
- [Недоступность ДО 3 при перезапуске] → проведение/перезапуск невозможны до восстановления связи; понятное сообщение
- [Неполный белый список] → лишние перезапуски; настраивать разрешённые реквизиты по мере эксплуатации
- [Сравнение ТЧ] → производительность на больших табличных частях; сравнивать только неразрешённые колонки
- [Подписка на все `DocumentObject`] → ранний выход по кэшу настроек обязателен для производительности
- [Рассинхрон регистра и ДО при сбое обмена] → до прихода статуса защита уже по факту связи с ДО; проведение по-прежнему только при `Согласован`; мониторинг обмена БИД остаётся нужен для UX статуса
- [Контроль включён без правила интеграции в ДО] → проведение невозможно, пока документ не согласован — зафиксировать в инструкции внедрения
- [Формы без `МодификацияКонфигурацииПереопределяемый`] → нет статуса на форме — серверный запрет проведения при этом сохраняется
- [ДО недоступен при перезапуске] → проведение отклоняется с текстом ошибки API; признак пересогласования сохраняется
- [Параллель с УХ-согласованием] → не смешивать в MVP; при конфликте приоритет этой change — только контур ДО
- [Обновление УХ] → расширение НП; риски только на заимствованных формах/переопределяемых модулях

## Migration Plan

1. Опубликовать расширение НП с объектами контроля
2. Включить интеграцию и согласование через ДО 3 в панели БИД
3. Создать правило интеграции для `ПеремещениеТоваров` в ДО
4. Добавить строки настройки по организациям: контроль + `ДатаНачалаДействия`
5. Заполнить белый список разрешённых реквизитов (минимум — заведомо «мягкие»: комментарий и т.п.)
6. При необходимости настроить отбор участников (исключения)
7. Проверить: проведение без согласования; дата раньше порога; существенные изменения + вопрос + перезапуск ДО 3; только разрешённые реквизиты без перезапуска; обход ролью
8. Откат: выключить `КонтролироватьПроведение` или снять расширение

## Open Questions

1. Нужен ли отдельный РС «проекция статуса» НП или достаточно чтения типового при каждом открытии формы (по умолчанию — без своего РС статуса).
2. Автопроведение после согласования — вне scope; подтвердить заказчику.
3. Список типов после пилота — отдельными строками настроек (по организациям).
4. Точный набор разрешённых реквизитов для `ПеремещениеТоваров` на старте — согласовать с заказчиком (в MVP можно пустой список = любое отличие шапки/ТЧ существенно).
